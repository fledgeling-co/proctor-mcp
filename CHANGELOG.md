# Changelog

All notable changes to Proctor are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Proctor can drive a Mac that isn't yours.** Attach a session to a macOS guest and every tool call from it runs inside that guest. The Proctor in there holds that machine's Accessibility and Screen Recording grants and talks to its own window server, so what you get back is a verdict about the guest, not about your desk.

  Here's how it works. Open the SSH StreamLocal tunnel that `proctor_guest reach` already describes, then call `proctor_guest` with action `attach` and the guest's name. Your calls are forwarded over that socket as they are. `proctor_guest`, `proctor_doctor`, `proctor_policy` and the history and queue verbs keep answering about your Mac, because the pool and the audit trail live here. Action `detach` points the session back at this Mac.

  The host actuates nothing for a guest session, and that's the whole point rather than a side effect. If the tunnel drops, the batch is refused with the guest named and nothing runs here instead. A verdict that looks fine and measures the wrong machine is the one outcome this can't be allowed to produce, so there is no fallback path to disable; the branch simply isn't written.

  Note: Proctor still creates no guest, installs nothing inside one, and grants no permission. Accessibility and Screen Recording are granted by a person inside the guest, once, and cloning that guest reproduces them.

- **Two macOS guests at a time, with a queue for the third.** That's Apple's limit on Apple silicon, not a setting we picked, and it's recorded in the code with that reason next to it. A third macOS guest waits in the queue and is told its position and how deep the line is, the same way a busy Mac lane already does. One session drives one named guest, so a second session naming the same guest waits for it even when a slot is free.

  The queue never evicts. A guest you started yourself, or one another session is holding, is waited for and never stopped to make room. Stopping a running VM throws away its state, and a scheduler allowed to do that to reach a queued run can destroy work nobody asked it to risk. Proctor only stops a guest it started.

  Which pool a guest joins comes from the platform its provider reports, never from its name. A guest whose provider won't say which OS it runs is refused rather than attached, because an unknown platform would sit outside the count and quietly break the limit.

  `proctor_doctor`'s guest lane now reports the pool: capacity, how many slots are held, by which sessions and guests, and how many runs are waiting. It's counted from Proctor's own scheduler, so reading it still runs no provider and starts no VM.

- **`tart` is a third guest provider**, beside `lume` and `prlctl`, on the same seam. Its listing doesn't carry the guest's OS, so Proctor reads that from `tart get` per guest rather than guessing from the name.

- **Proctor now has a command line, and it isn't a second way in.** `proctor` gives you 21 verbs, one per tool, so you can drive and check this Mac from a shell without a model in the loop. The verbs come from the tool catalogue rather than a list somebody maintains, so a new tool can't ship without one. Shell completion is generated the same way, for zsh and bash.

  A CLI call takes the same socket as the MCP shim, passes the same policy gate, joins the same queue lane, lands in the same audit trail and shows on the same run HUD. The only thing that differs is who called, and the trail now says which: every row records whether it came from the CLI or from a model. That's read from the process on the other end of the socket, not from the request, because a caller that could name itself could name itself as the other one in the very record you'd argue from.

  Six exit codes, and two of them are the point. 1 means the call worked and your check failed. 3 means the agent isn't answering and nothing was measured. CI reads an exit code rather than prose, and collapsing those two turns "the app is broken" and "the agent isn't running" into the same signal.

  Note: reads never queue. `proctor snapshot` won't wait behind a model's run, because a read-only tool never reaches the step loop.

- **`proctor tui` gives you a Stop button over SSH.** Supervision used to be a floating panel and a window, and both need a graphical session on the machine being driven. Working over SSH you saw no run line, no queue, no history, and had no way to halt anything. The kill switch existed and you couldn't reach it.

  Five panes now: **run**, **queue**, **readiness**, **history** and **switches**, each one keystroke away. Frames are pushed from the agent rather than polled, because a supervision screen that polls shows you stale state exactly when a run is moving fastest, which is the moment you're deciding whether to press Stop. Press `s` and it writes the same latch the on-screen panel writes; there's one, not two.

  It works at 80x24, which is the size that still exists everywhere. It holds no permissions and needs no window server.

  Note: it watches and it halts, and that's all. It issues no tool calls, authors no flows and edits no policy. The surface that reaches furthest is deliberately the one that can do least.

- **A fidelity harness that says what settled a comparison.** `SurfaceFidelity` names the channel behind every check: the accessibility tree, the layer, the pixels, or nothing at all. When nothing could measure a property it returns inconclusive with the reason, rather than a pass.

  That last part matters more than it sounds. The Reflector walks AppKit views, so a SwiftUI subtree shows up as its hosting view and whatever backing views SwiftUI happened to create. There's no supported way to read a resolved SwiftUI modifier value from outside the framework. Identifiers, roles, geometry and pixels are settled properly; a style that SwiftUI never puts in a layer comes back as inconclusive and says so.

- **`proctor_guest` status now tells you which macOS a guest is running.** Ask for `status` and you get an `osVersion` beside the guest and the machine. Where Proctor can establish it, that's the version the Proctor inside the guest gave when it was asked. Where it can't, you get `unknown` and the reason, naming what would change the answer.

  Here's how it works. No provider records a guest's OS version: `lume get` and tart's `config.json` both report only `macOS` or `darwin`, and `prlctl` is no better. The only thing that knows is the machine itself, reached over the link an `attach` has already opened. A stopped guest, a Linux or Windows guest, a guest this session isn't attached to, and a guest whose Proctor doesn't answer each get their own reason rather than sharing one.

  It's never guessed from the image name. A guest called `macos-sequoia-cua` reports `unknown` until something inside it answers, and a session attached to one guest never reports that guest's version in a status about another.

### Changed

- **The statement said Fake because the test suite was drawing it.** Reported from real use: the full-screen tint read `Proctor is driving "Fake"`, always that word. No app on this Mac is called Fake and no shipped string contains it. It's `FakeAX`'s app handle, out of the test fixtures, and it was reaching the screen because `Session` defaults to the live takeover driver and most of the wiring suites build a session without replacing it.

  Measured while one suite ran, with the gate removed to prove the check bites: two windows from `swiftpm-testing-helper`, one at the tint's own level part way through its fade, one at the drawn pointer's. With the gate in place the same run paints nothing.

  The switches couldn't have caught this. `PROCTOR_TAKEOVER` and `PROCTOR_CURSOR` are on when unset, which is right for the agent and wrong as a default for anything else linking the same code. A switch says what an operator asked for; it can't say who's asking. So entitlement is claimed now, by the one entry point that can honestly claim it, and a surface whose switch is on still draws nothing until the agent has said so. The input block was already opt-in, so it was never armed this way, and it goes through the same gate anyway rather than staying safe by luck.

- **No drawn pointer over an app you cannot see.** The pointer belongs in its target window's own plane, so a window covering the app covers the pointer too. When that placement could not be confirmed it used to fall back to floating above everything, dimmed, to say it could not vouch for the position. Over a covered window that is the one picture the pointer exists to avoid: it reads as Proctor clicking the app you are looking at while it is driving a different one, and dimming it does not stop it being that picture.

  The fallback now splits. Nothing covering the target: float and mark it, as before, because the pointer is where it would be anyway and only the exact ordering is unconfirmed. Something covering it: draw nothing. Proctor's own panels do not count as covering, or the pointer would vanish from every window it ever annotates.

- **The overlay stops flashing.** It was raised for a batch and lowered when the batch ended, which is fine when a person drives Proctor and wrong when a model does: agents send a handful of steps at a time, several times a second, so the statement went up and down every second or two. It now stays up for at least three seconds once raised, and a request arriving while it is up extends it instead of raising it again. A busy run shows one statement for as long as the work lasts rather than a strobe.

  Three seconds is the run panel's own linger, so the two come down together instead of one explaining a statement that has already gone.

- **The takeover statement points at a control you can actually reach.** The statement is drawn on every display. The run panel stands on one, the screen holding the window being driven. So if you watch Proctor work on a second monitor, you read "Pause and Stop are in Proctor's run panel" while looking at a screen that has no panel on it. That's the confusing part, and it's why the HUD sometimes seemed to be missing when the overlay was up: the statement is right in front of you and the thing it names isn't.

  The line now changes with the screen reading it. On the panel's own display it names the panel. Everywhere else it names Proctor's menu bar, which is reachable from whichever screen you're on. A run with no panel anywhere gets the same treatment, whether it was switched off, hidden from the menu bar, or taken down after a drawing fault; every display names the menu bar, because that's where the controls are in that case.

  Which display holds the panel is asked of the same placement arithmetic the panel used to pick its screen, so the label and the panel can't disagree about where it is. The held wording doesn't vary: Esc isn't on a screen.

  Pressing Stop still takes it down at once, including when the statement was left up by an earlier batch. "Proctor is driving this" stops being true the moment you stop it, and a minimum duration is a courtesy to whoever is reading, not a promise to keep a claim on screen after it is false.


- **The app's colours are generated from the design, so they can't drift from it.** A build plugin reads the tokens out of the mock's own stylesheet and emits them as Swift. A colour in the app can no longer disagree with the colour in the design, because there's only one place either of them comes from.

- **Seven surfaces rebuilt on tested values.** The status window, the setup walkthrough, the menu bar, the run HUD, the takeover notice, the history window and the consent sheets are each drawn from a pure surface value with its own tests, rather than from literals spread through a view.

  The menu bar went from 1 command to 20, and a test asserts every one of them actually renders. The history window counts a skipped check as skipped: never as a pass, always with a reason. A check that couldn't run isn't a check that passed, and a product built to catch that failure shouldn't commit it in its own UI.

- **The menu bar is complete, and the permissions list is honest.** Three commands were declared for the menu bar and never appeared in it: clearing the queue, and the two switches that decide whether Proctor announces itself. They are there now. Clearing the queue needed a route of its own, because the queue's controls and the run's are deliberately different words on different rows; Hold, Release and Clear act on the line, Pause and Stop act on the run in flight, and a person who meant one and got the other has no way back.

  The permissions list also gained the one permission whose absence is silent. Input Monitoring gates the keyboard event tap, so an operator who turns the input block on can find it quietly unavailable, and a list that omitted it was the list that most needed it. Proctor already read it; it just never said so.

  Note: a check that could not run is not a check that passed. The status window still draws its permission rows from a build-time list rather than from the design, and that gap is recorded rather than papered over.

- **The design of record now says what the app says.** The status window and the setup walkthrough each explained more than the design drew: a title block, a line saying every permission is granted, and a first slide leading with what Proctor does rather than a row of capability chips. These are the two screens that ask for the most invasive permissions macOS has, so the extra words stay and the design was updated to carry them. The design was also short a permission, and Automation is in it now.

- **Supervision over SSH reads the machine, not just the run.** The readiness, switches and history panes were drawing their empty state whatever the Mac was doing. They now show real grants, real lanes with what each still wants, every switch with where its value came from and when it takes effect, and the recent runs with what each one drove and how it ended.

  History was nearly left out, on the reasoning that the trail is sealed and no client can read it. That was wrong twice over. The verb the History window uses already exists, and keeping it off the tool catalogue was never what kept a model out of the trail, because the policy tool already opens the trail and hands back whole records. The pane reads the same projection the window reads, which is narrower than what a model can ask for anyway, so nothing here opens a path that wasn't open already.

  Three states used to look identical and no longer do: a Mac that has recorded nothing, a trail this Mac couldn't open, and a history that opened short. The last one says how many entries it couldn't read, because a history one row short reads as a complete history of a quieter machine.

- **An assertion in the test suite that could not fail, and five tests nothing was counting.** A scan for Swift assertions that pass while testing nothing found one real hole: a test whose whole claim is that a captured build identity does not move when the file underneath it is replaced was comparing a stored value to itself. It would have passed on exactly the build it exists to catch. Three more asserted only by not throwing, which passes just as happily with the guard deleted, and they now say so.

  Arming the scan found a fault in the scan, which is why you arm it. A one-line test body balances its braces on the signature line, so the finder skipped it and then read the next function's body instead. Fixed, and the count of tests it can see went from 1,648 to 1,653.

- **`proctor act` can now actually act.** Eight of the twenty-one verbs take a list or an object as their main argument, and none of them could be given one: every flag value was turned into a string, a number or a boolean, so a step batch arrived at the agent as text and came back "requires steps as an array". Pass JSON to a flag and it stays JSON, or pipe an object of arguments with `proctor act -`. A flag beside the pipe wins, so you can retarget a recorded batch at a different window without editing the file.

  The first version worked out whether to read the pipe by asking if it was talking to a terminal. That is true and not enough: a CI runner and an agent harness both hand you something that is not a terminal and not a pipe anyone writes to, and `proctor doctor` sat there forever. Asking for the pipe with `-` cannot hang.

- **The iOS lane's live tests can run on a Mac with more than one simulator booted.** They passed no device and relied on there being exactly one. Proctor was right to refuse that and name the four it found, so the whole live lane went red for a fact about the machine rather than about the code. They take a device now, and where the machine cannot say which one they do not run, because picking one on your behalf would drive a simulator you might be using.

  Running them also turned up a second thing: both tests drive one simulator, and run together they interleave on it. The determinism check scored its own two repeats as divergent because the other test was tapping the device mid-repeat. They run one at a time now.

- **The run panel's provenance chip had the same problem, found the same way.** Widening the mutation run from four files to all of the core came back at 50% survival, and among the survivors was a chip comparing how many fields two chips have. Nothing had ever compared two chips with different counts, so a chip that lost a field read as the chip that has it: the panel would keep showing the previous step's provenance for the current one. Both of these are hand-written comparisons over lists of pairs, which Swift cannot write for you, so they are the shape that goes wrong quietly.

  Two other survivors were left alone on purpose. Neither can be killed by any test: one sits behind a check that already catches every value that would reach it, and the other distinguishes two cases that cannot both occur. A test contorted to kill an unkillable mutant is worse than the mutant.

- **The supervision model's equality could not tell two models apart.** Nothing in 1,666 tests noticed, because nothing was looking: a mutation run over four core files came back with 10 of 24 mutants surviving, and every one of the ten was in that one hand-written comparison. Flip an `&&` to an `||` in it and two models that differ read as identical.

  Nothing in the app calls it yet, which is why it survived and why it was worth fixing rather than leaving. The obvious speed-up for the terminal surface is to skip a redraw when nothing has changed, and a comparison that cannot spot a change turns that into a screen that quietly stops updating while a run is moving. Every one of its thirteen fields is now pinned, and a field added and forgotten fails on a count before it can go out.

- **A halted run no longer tells you where it was stopped from.** Stop is reachable from the run panel, the menu bar and the terminal, and they all write the same latch, so a message naming one of them was wrong two times in three. It names what happened instead.

The gate is now 1,814 tests in 214 suites, from 1,516 in 175 when this release started.

- **The Tahoe guest warning now carries its measurement instead of a verdict.** `proctor_doctor`'s guest lane, the `proctor_guest` description and every `proctor_guest` result used to tell you flatly that Tahoe guests render no application windows, and to go and verify against Sequoia. Both upstream reports are real and both are still open (trycua/cua #870, Apple FB21748086). What the note left out is that Proctor drove a macOS 26.6.2 guest on 2026-08-21 in which Calculator, System Settings and Setup Assistant all rendered normally.

  You now get the reports, the measurement, the date and the machine in one sentence, and you can weigh it yourself. This isn't a claim the bug is fixed; one guest on one host at one version settles nothing. It's the difference between reading a hedged finding and reading a verdict, and the verdict had someone about to download a different macOS image on the strength of it.

  The advice to verify against Sequoia is gone, because status is the version of that instruction you can actually act on. There's one copy of the sentence now rather than three hand written ones, and a test binds what it states back to the spec section that recorded the measurement, so the note and the record can't quietly drift apart.

### Fixed

- **When another program is driving your Mac, the run panel now says so properly.** Run Proctor with `PROCTOR_ACTUATION=cua` and cua-driver performs the steps instead of Proctor's own planes. Two things about that used to reach the run record and never reach the screen, which is where you're actually looking.

  The first is an escalation nobody asked for. cua-driver tries an accessibility action, then an event routed to one process, and only brings the app to the front when neither works. It decides that per element, so it can happen partway through a batch that never requested the foreground. The panel used to say the batch needed the front, which is a different claim. It now says the front was taken and the batch didn't ask for it.

  The second is whose cursor you're watching. If the installed cua-driver can't be asked to stop drawing its own cursor, Proctor stands its drawn pointer down rather than put two cursors on one screen. That left a real cursor moving with nothing on screen to explain it, which looks exactly like your own mouse misbehaving. The panel now names the driver as the thing moving it.

  Note: Proctor can't hide the driver's cursor when the target window is covered, and that limit is now recorded in the code rather than worked around. The covered-target rule works by moving or hiding a panel Proctor owns, and a cursor drawn by another process isn't one.

- **A capture that came back empty used to pass as a good one.** Ask for a picture of a window Proctor owns and you'd get `status: complete, trustworthy: true` over a PNG in which all 2,942,720 pixels were fully transparent. The exclusion was doing exactly what it should; Proctor keeps its own windows out of its own captures so the run HUD never turns up in a shot. Nothing in the reply said so, and `dirtyArea 0` sitting next to `dirtyRectCount 1` reads as though something changed.

  `SCFrameStatus complete` means a frame arrived, not that the frame depicts anything. The verdict now asks whether there's anything in it before vouching for it. An empty frame comes back `trustworthy: false` with the reason in plain words, and where Proctor owns the target it states the mechanism rather than guessing from pixels: this window is excluded from capture, so nothing was going to be in it.

  Every reply carries a **`content`** block now, with the number of pixels examined, the highest alpha seen and how many distinct colours. Alpha is read over every pixel rather than a sample, because a stride over a 3456x2234 frame steps 7 or 8 pixels and would call a one pixel hairline an empty window.

  There's a third answer beside "there's something in it" and "it's empty", and it's the one that used to say nothing: a frame whose bytes arrived in a layout the summariser can't read, either not 32BGRA or a buffer shorter than its own geometry. That came back `trustworthy: false` with no reason attached, on the reasoning that a check claiming nothing owes no explanation. It now names the window and says what couldn't be done, worded so it doesn't imply the window was empty; a measurement that never ran has no standing to call anything empty.

  Note: a legitimately blank window is still a pass. An opaque single colour frame is content, not a fault; `distinctColours` is reported so you can make that call yourself, and nothing in the verdict keys off it.

- **The drawn pointer was the one overlay you could photograph.** The run HUD and the takeover statement both set `sharingType = .none`, which keeps them out of every capture channel on this Mac. The pointer set it nowhere, and it's the only one of the three that changes window level while a run is going. Assigning a level resets the sharing type, so it sat at `sharingState 1` on the window server while its two siblings sat at 0.

  Level and sharing type are set together now. Measured on two signed builds differing in that one file, sampled from a separate process: before, the agent owns three windows and one of them is capturable; after, it owns three and none are. That also settles what a fourth window nobody had identified actually was, which was this one.

- **Proctor's policy file was written with looser permissions than everything beside it.** `policy.json` came out `-rw-r--r--`, whatever your umask happened to give it, while the audit files in the same subsystem have always been opened `0600` deliberately. The folder they share is `0700`, so nobody else on the machine could reach the file; that's why this was an inconsistency rather than a hole. It stops being one as soon as the file is copied, backed up, or that folder's mode is relaxed by something else, and the file is the record of which applications an agent is allowed to drive.

  It's now created `0600` by the call that creates it, rather than tightened afterwards. A file that existed world-readable for an instant has been world-readable, so the mode is set at the open rather than fixed a moment later. If an earlier build left you a wider `policy.json`, the next save narrows it.

- **Running the test suite used to edit your Proctor policy.** `PolicyStore` worked out its own path from your home directory, so a test that configured a policy wrote the real file at `~/Library/Application Support/app.fledgeling.procter/policy/policy.json`. Nothing announced it and nothing put it back.

  The read was the wider half. Every session in the suite that didn't say otherwise loaded that same file, so the whole run inherited whatever policy you had configured. On a Mac with an empty policy that's invisible, because an empty policy allows every app; on a Mac with an allow list in force, tests that never mentioned a policy start refusing apps they've never heard of.

  `PolicyStore` now takes the directory it should use. Production hands it the real path, and in a test process a store nobody pointed anywhere gets a fresh empty temporary directory of its own. Not by writing your file and putting it back afterwards: a restore that doesn't run, because the process was killed or an assertion threw, leaves your policy changed and says nothing about it.

- **A test was measuring this Mac rather than the product.** The bounded Screen Recording probe was checked with a stopwatch, `elapsed < 5.0`, and it failed six times in one wave at 5.6s, 6.1s, 6.58s, 8.13s, 10.25s and 14.73s. The probe answered correctly on every one of those runs; what moved was how busy the machine was.

  The thing that ends the wait is now told to the probe rather than buried inside it, so the test watches that mechanism fire and reads no clock at all. The bound itself is unchanged at 1.5s. Raising it would have made the test fail less often while saying nothing more about the product than it already did.
- **A Mac running several Proctor sessions could stall for minutes on a health check.** Proctor caches what `cua-driver`'s code signature says so it doesn't re-hash an 82 MB binary every time you ask. The cache was built per session rather than per machine, so fifteen sessions each verified the same file at the same time, at 0.5 to 0.9 seconds a go. That filled every thread Swift gives the process, which meant unrelated work couldn't run at all: calls sat unanswered, and a caller with a ten-second timeout gave up before Proctor got to it. One process now verifies a given file once, however many sessions ask and however many ask at once. The ones that arrive while a check is running wait for that answer instead of starting their own, and they wait without holding a thread, so the rest of the process keeps moving. The check itself is unchanged.

- **The guest lane's `attach` and `detach` were advertised and refused.** The tool catalogue listed them, and a second copy of the action list inside the dispatcher didn't have them, so the call was turned away before it reached the code that handles it. That second list is gone rather than corrected. The session code already switches on the action and already refuses an unknown one with the same message, so the only thing the copy ever added was somewhere to drift, and the two actions it had fallen behind on happened to be the entire feature.

- **Proctor couldn't see your `lume` guests.** The listing asked for `--json`, which lume 0.5.3 rejects by name, so every guest came back empty and the lane reported that lume wasn't usable on this Mac. It now tries `ls --format json` first and falls back to the older spellings, and reads a single guest's state with `get <name> --format json`.

- **A guest agent crashed on startup instead of running without its resources.** Two places in Proctor look up a bundled resource and are written to carry on when there isn't one. `Bundle.module`, the accessor SwiftPM generates, only looks at the top level of the `.app` and at a build path from whichever machine compiled it, then stops the process dead rather than returning nothing. In a shipped app it never finds the bundle, so a build installed anywhere else crash-looped on launch. Resource lookup now searches the places a bundle actually sits, `Contents/Resources` included, and hands back nothing when there's none to find.

- **A result from a guest could read as a result from your Mac.** When a call is forwarded to a guest, the guest answers with its own description of the machine it ran on. That description was passed straight back, so the reply said "host" while the work had happened inside the VM, which is the one thing this feature can't be allowed to get wrong. The top-level machine on a forwarded reply is now stamped with the guest you attached to. Anything nested is left alone: that's the guest describing something else, and rewriting it would be this Mac inventing content rather than passing it on.

- **A macOS guest calling itself `darwin` was classified as Windows.** The platform check tested whether the provider's word contained "win", and dar-win contains it. Any guest whose provider named its platform honestly came back as a Windows machine: it took the delegated witness tier, lost the accessibility tree and the frame-status channel it actually has, and was refused by `reach` as a machine with no Proctor inside.

  Matching is now on a whole token that starts with "win", so `win`, `win11` and `windows` are still Windows and `darwin` isn't. This has been latent since the guest providers shipped and only surfaced because `tart` is the first provider here that says `darwin` rather than `macOS`.

- **The takeover report could claim somebody fought a hold nobody touched.** Mutation testing over the new code turned up three live gaps in the sentence Proctor writes after it has held your keyboard, and this was the one that mattered: the clause that reports interruptions was guarded by "more than zero", and flipping it to "zero or more" left every test green. A run nobody touched would have reported that somebody used the machine 0 times and those events did not reach the application.

  The other two: the held duration divided by 1001 instead of 1000 and nothing noticed, because the only value under test rounded to the same string either way. And the option modifier could be given the same bit as control, which would let a release chord accept the wrong key, with nothing asserting the four flags were distinct.

  All three now have tests, and all three were watched to fail before being trusted.

- **`proctor assert` told you your check passed when it had failed.** The CLI decides its exit code from the agent's reply, and the branch that reads a failed assertion was looking for a key the reply has never carried. It checked each assertion for `ok`, and assertions report `status`, one of pass, fail or skipped. Missing key, no match, exit 0.

  So a failing check exited 0, and so did a `wait` that timed out. That is the one thing this surface exists not to do: CI reads an exit code rather than prose, and it was reading success off a reply whose own JSON said the check had failed. `kill` had it too, reporting failures in a top-level count nothing looked at.

  It now reads the top level first, which is where every verb puts its answer. Exit 1 means the call worked and your check didn't; exit 3 still means the agent never answered and nothing was measured.

  The test that should have caught this built its own reply in a shape the product doesn't emit, so it passed against a fiction for as long as it existed. The replacement is built from a real reply, and it comes with a control: a passing check has to still exit 0, or a fix that just fails everything would look identical.

- **The setup walkthrough let you continue without the permissions it was asking for.** On the permissions step, "Connect a model" was drawn enabled whether or not Accessibility and Screen Recording had been granted. The design of record has that control visible and disabled until both are in, and the build had it live the whole time.

  It's now disabled until both grants land. The decision comes from a pure function in Core, `WalkthroughFlow.primaryEnabled`, tested at all sixteen combinations of its inputs, rather than from a condition inside a view body where nothing can check it.

  The control dims in place rather than disappearing. A control that vanishes makes the layout jump and teaches you the step isn't there at all. "Skip setup" stays enabled throughout, so a grant macOS won't give you is never a dead end.

- **`tart` was missing from the guest tool's provider list.** Proctor has driven tart guests since the third provider landed, and `proctor_doctor`'s guest lane named all three, but `proctor_guest`'s own schema enumerated `lume` and `prlctl` only. Passing `provider: "tart"` was refused by validation before it ever reached the code that handles it, and a reader going by the tool description reasonably concluded tart wasn't supported. The schema, the description, the field docs and the refusal you get for a missing guest all name three providers now.
- **`PROCTOR_OVERLAY_CAPTURE` makes Proctor's overlays photographable, for testing them.** Off unless you set it, and worth understanding before you do. The exclusion above is absolute: with it in place there is no way at all to photograph the run panel or the takeover notice, which also means nothing can check what they draw. Setting this to `1` drops the exclusion on all three overlays for that run of the agent, so a test can capture them and compare. While it is on, anything recording your screen sees them too, so leave it off outside a test.

### Fixed

- **Proctor's own window can now be used by a screen reader.** A tool that reads other applications through the accessibility tree owes its own surface the same standard, and it was not meeting it. Every switch in the Switches card was built with an empty label, so all nine reached the accessibility tree as checkboxes with no name at all: VoiceOver announced nine identical unnamed controls in a column. The seven Details buttons in the Tools card were all called "Details", with nothing saying which tool each belonged to, and the permissions list repeated "Open Settings" and "How" once per grant. Each control now carries its own name: the switch says what it switches, the disclosure names its tool and whether it will show or hide, and the permission controls name their permission. Measured on the installed build: 9 named checkboxes, 21 buttons, no two alike.

- **`scripts/install.sh` no longer installs a build older than your code.** Rebuilding re-signs the app, and re-signing throws away a notarisation ticket, so the installer reuses a bundle that is already notarised rather than making you wait through notarising again. That was right until the source moved: it went on reusing the old bundle, printed `notarised: yes`, and finished with what looks exactly like a successful install. It caught us twice in one afternoon, and the only way to spot it was reading the timestamp on the installed binary. The installer now compares the bundle against `Sources`, `Apps` and `Package.swift`, says plainly that the bundle is older than the source it was built from, and rebuilds. Set `PROCTOR_REUSE_BUNDLE=1` if you want the old behaviour for a moment.

- **The status window notices an agent that has stopped answering.** Killing the background agent was always reported within a couple of seconds, because the connection fails immediately and there is nothing to wait for. An agent that is still running and simply never replies is the harder case, and the window sat on it: the check that reads the agent blocked forever, the next check never started because the previous one had not finished, and the window went on showing Ready with green permission ticks against a machine where nothing could run. Held that way deliberately, it stayed wrong for as long as we watched. The window's own checks now give up after five seconds and say so; the background agent is told it is not answering rather than assumed to be fine. Nothing changed for a model driving Proctor, whose calls are meant to take as long as the work takes.

- **Proctor's drawn pointer no longer lands in your screen recordings.** The run panel and the takeover notice are kept out of screen captures on purpose, so a screenshot of your app is a screenshot of your app rather than of Proctor watching it. The drawn pointer was supposed to follow the same rule and did not: it covers every display, so anything recording the screen during a run picked up Proctor's own cursor. It sets the exclusion at the same moment it sets its position now, which is the part that was missing; it moves between window layers as it follows a target, and the exclusion was being dropped each time it did.

- **Proctor's window comes back when you reopen it.** Once setup is done Proctor lives in the menu bar, so closing the status window leaves the app running with nothing on screen. Reopening it from the Dock, with `open -a Proctor`, or by double-clicking Proctor in `/Applications` brought the app to the front and stopped there; no window appeared and nothing said why. The check behind it asked macOS whether Proctor had any visible windows at all, and the menu bar item counts as one, so the answer came back yes for an app showing nothing. It now asks the narrower question, whether the status window itself is on screen, and orders it front or opens it. **Window ▸ Proctor** in the menu bar always worked and still does.

## [0.2.0] - 2026-08-17

### Added

- **A run can target a guest, and it says which machine it is on.** Synthetic steps (click, key, hover, dragPath, and type when accessibility cannot write) enter the single system event stream, so they take this Mac. They can now land in a guest instead. Every act result, stability report, audit row and doctor report names the machine; the default is still this Mac, so nothing that existed before this behaves differently.

  Two witness tiers keep a Linux target from passing itself off as a macOS one. A native guest (a macOS VM or a remote Mac running a full Proctor) keeps frame status, the accessibility tree, `agree`, fidelity and determinism. A delegated guest (Linux or Windows through Cua) is actuation and screenshots only; every tree-reading assertion comes back skipped with a reason, never as a weaker pass.

  `lume` and `prlctl` are the two adapters. Detection is a filesystem read and never an execution; either provider is enough, and a health check does not list guests. Presence settles usability. `proctor_guest` lists, starts, stops and clones machines that already exist, and refuses a `gst-` handle from every window tool by name. Nothing provisions. The TCC story is grant once inside the guest's GUI session, then clone; that recipe is documented, not automated.

  `reach` describes an SSH StreamLocal tunnel onto a native guest's unix socket (localSocket, remoteSocket, host) and never returns a shell command. Delegated guests are refused here and named as Cua's. The same recipe reaches a remote Mac over Tailscale.

  Auto-route is a gate, not a silent host run. A takeover batch with `PROCTOR_GUEST` set is refused on this Mac and names the guest, because this process cannot yet perform a step inside one; running it here while naming that guest would be a verdict about the wrong machine. A press, which does not take the Mac, is not refused.

  On a guest the overlay says `On <guest>. This Mac is free.` The takeover statement, the input block and the contention yield are all claims about this machine, so they stay down.

  Note: Tahoe guests currently render no application windows (trycua/cua #870, Apple FB21748086). Verify against Sequoia. The gate after this wave is 1512 tests in 174 suites, from 1426 in 158 when it started.

- **Screenshots now cost what the job needs, not what the vision API tolerates.** Proctor used to send every capture at the ceiling, roughly 1,530 tokens a frame whether or not anything in it needed resolving. Captures now come in three sizes and default to the middle one: 768 pixels for deciding what to press, 1,024 for checking what happened, 1,568 for reading dense text. Asking for numbered marks drops to the smallest on its own, because a numeral survives a downscale that body text does not. Measured on a 16 inch Retina window, the new default costs 816 tokens against 1,532, and a targeting frame costs 459. Start small and reach for `proctor_zoom` when you need detail; a low resolution overview plus an on demand native crop reads better as well as costing less, lifting grounding accuracy on dense interfaces from under 20% to over 70% in published measurements. Every capture reports which tier it used and roughly what it cost, and the tool now says plainly that `proctor_find` and a step's own `stateHash` answer "what can I press" and "did that change anything" for a fraction of an image.

- **A run that is being held now says so, instead of looking slow.** Pause and Stop hold a run between steps, and a hold that nobody lifts used to be invisible: the run simply stopped producing steps, and from outside there was no way to tell a held run from a wedged one until the fifteen-minute backstop gave up. After twenty seconds a held run now writes one line naming which run it is, what is holding it, and when it will give up. The backstop itself is unchanged; how long your pause may hold a run is your decision, and shortening it would turn a wait into a wrong answer.

- **A determinism score now says what it was a score of.** `proctor_stability` replays a recorded flow several times and reports how deterministic each step was. That score is built from a walk of the window's accessibility tree, and inside a browser's web area that tree is the page's own render tree rather than the application's view hierarchy; a score taken there measures the page's churn as much as the app's. Proctor already knew this, already carried the sentence saying so, and already showed it to you when you drove a step. The stability report was the one surface it never reached.

  It reaches it now, **per step**. A flow that clicks a toolbar button and then something on the page has steps of both kinds, so the report says which side of the boundary each step fell on, and names the browser and the steps concerned once. A single flag on the whole report would have marked the reload button suspect along with everything else.

  The score is still there. Nothing is withheld for being page content: a flow that agreed across five repeats agreed, and saying which tree it agreed in doesn't make that less true. What the disclosure does is name what the number is about. It doesn't turn a measurement of the page into a measurement of your application, and it isn't written as though it does.

  The classification is taken while the step runs rather than by reading the flow beforehand, and that's the difference between describing the common case and missing it. A step's target usually doesn't exist until the steps before it have run, which is exactly what clicking a link and then driving the page that opens looks like. Scanned up front, that flow would have been described as touching no page at all while still publishing the page's number.

  Second, and this one is a fix rather than a disclosure. When the driver process dies mid-step, Proctor records the step as **indeterminate**, because it can't say whether the action happened, and it reads the window anyway as the only evidence left. That reading was being folded into the determinism score as though it were a step that ran. Measured on this build: a two-repeat sweep whose second repeat died that way reported `deterministic: true`, because the reading happened to match the good repeat and filled the column. The reading is now kept on the step as evidence and refused by the score, and the sweep says what it should.

  Third, each step says how many repeats its score was folded from, and no number is published at all below two. The maths returns zero for a single sample, so a step measured once was indistinguishable from five repeats that agreed.

  Note: a window no browser renders is untouched and pays nothing for any of this. The check is a bundle-identifier lookup, and only a browser window goes on to read its web areas. Reports written before this still read fine, and a run against a native app encodes exactly as it did.

  Note: an app that is Chromium rendering one site, Slack or VS Code say, is deliberately not treated as page content. For the purpose of testing one of those, its render tree is its interface.

- **Supervision keeps working when Proctor isn't the one clicking.** Proctor has started handing its clicking and typing to a separate driver process, and four things you rely on were built assuming Proctor posts the events itself. A driver's click on a control that happened to sit under the run panel's Stop button would have stopped the run you were supervising. A hold one run put on the keyboard would have swallowed a second run's driver events and left its steps quietly doing nothing, because two runs on different apps genuinely happen at once and the hold is one tap for the whole process. Proctor drew a pointer and so did the driver. And if the driver's events ever looked like a person's, the run would have held itself until it gave up. The rule that recognises Proctor's own actions now admits exactly one more identity: the driver's own process id, checked against the signed program Proctor already verified, and honoured only while Proctor has asked it to act plus a fraction of a second afterwards, so the end of a drag isn't stripped off. Both the event tap and the run panel read it, since widening one and not the other just moves where the wrong click lands. A driver Proctor can't recognise makes its run wait for the whole machine rather than share it, and hold nothing at all; switching off a hold another run is keeping would drop a guard over a person. Exactly one pointer draws, decided once per run. Proctor's draws and the driver is asked to stand down on every action; where it can't be asked, Proctor's own stands down instead, because that's the half Proctor can switch off with certainty. `PROCTOR_CURSOR` means exactly what it did and gains no reach over the driver's cursor, and `proctor_doctor` says so rather than leaving you to infer it. Nothing the driver writes reaches the panel's words, and where its text does reach you it's cleaned up, cut short and marked as the driver's. The rule for whether an event should hold the run is untouched, because it was already written the safe way round: only something from the hardware counts. Note: on this lane the full-screen statement that the machine has been taken can only go up after the first time it happens, since nothing outside the driver's process knows before it does, and the run says afterwards that the warning was late. What is knowable up front is on the panel from the start. Note: the driver isn't installed on this machine, so what Proctor expects it to report is read from its documentation; every part of that fails closed, so being wrong costs a serialised lane or a pointer that doesn't draw rather than a guard that silently isn't there.

- **Maestro flows now run as Proctor flows, and the score says what it's a score of.** `proctor_ios` gains a **flow** action that runs a `.maestro` YAML file against a booted simulator, and with `runs` above 1 it scores the repeats. That last part is the interesting half; repeating a flow five times and measuring the variance is genuinely useful and nothing else on this platform packages it.

  What it proves is coarser than a Mac replay, and the result says so rather than borrowing the stronger words. Maestro executes a whole file and reports at the end, so **flowPassed** means the driver executed the sequence and reported success; it doesn't mean Proctor observed the app reach a state. Proctor didn't run those commands and the only observer of them is Maestro itself. Proctor adds two channels of its own, process liveness and device frames, but they bound the run rather than sitting between commands, because observing between two Maestro commands would mean driving them. Individual Maestro commands are never routed through `proctor_act`, for the reason the browser lanes were settled on: a tool driving its own engine isn't driving the window Proctor is attached to.

  The score hashes each command's identity and whether it completed, ordered by Maestro's own sequence number. Durations are reported next to the score and never inside it. One unchanged command measured 634, 91, 88, 96 and 91 ms across five repeats, so a score that hashed a duration would report a perfectly stable flow as totally unstable. **firstDivergence** here is repeat against repeat, never against a recording, because there is no recording; the index is a Maestro sequence number rather than a line of your YAML, and Maestro prepends two commands that are in no flow file, which come back marked `injected`.

  A repeat that failed in the driver rather than the app is dropped from the score and marks the sweep truncated, so driver flake is never published as the application's non-determinism. Exit code can't tell the two apart: an assertion failure, a device that doesn't exist and a malformed YAML all exit 1, and what separates them is that only the assertion failure writes a per-command record. A failed `launchApp`, `runScript` or `runFlow` is the harness failing rather than the application under test, so those are excluded too. Note: dropping them makes the surviving figures an optimistic bound, and the run notes say so rather than leaving you to work it out. What's left is genuinely inseparable and is stated instead of claimed away; a tap or an assertion that failed because the simulator was loaded or the driver's hit test missed looks exactly like the app not showing what it should. The failing assertion in the measurements ran 17,289 ms against 130 to 2,000 ms for the commands that passed, which is characteristic and still not discriminating.

  A flow file is content Proctor executes, so the gate reads it first. It judges the apps the flow **declares**, which is weaker than the device-resolved judgement the deep-link action makes, and every field carrying them is named `declared` for exactly that reason. Anything Proctor can't resolve is refused whenever an application policy is in force and reported when none is: a `runScript`, an interpolated app id, an include it can't read, a YAML anchor or alias. A `runScript` comes back classed as a **capability** rather than an unresolved app id, because it runs JavaScript with network access and an application allow list doesn't govern egress. An `openLink` inside a flow is gated on what the device resolves it to rather than on the file, and a `config.yaml` sitting beside the flow is scanned with it, since Maestro reads one implicitly. The trail records the flow's path and a hash of its contents, so an entry attests to the bytes that ran and a flow edited between two runs shows as two hashes rather than one filename.

  Proctor detects Maestro and never installs it, and the result carries no command text. Note: Maestro's own analytics are enabled by default in its own config, which is disclosed in the run notes; Proctor doesn't rewrite that file, because it belongs to whoever set it up. A five-run sweep costs 70 to 90 seconds, most of it JVM start-up, so `runs` defaults to 1 and you opt into the cost.
- **The `PROCTOR_*` switches have a home.** Eight environment variables decide how Proctor behaves while it runs, and until now they lived nowhere. An environment variable leaks into every child process the agent spawns, it's invisible once set, and the only way to change one was by hand. Somebody who'd turned something on had no way to see that it was on. The status window now has a **Switches** card carrying all eight: the **run panel**, the **drawn pointer**, the **takeover notice**, **yielding to a person**, **watching input**, **holding the keyboard and mouse**, the **second browser lane**, and **delegated actuation**. Each row says what the agent is running with, what you've saved, and where the value in force came from.

  Precedence has two parts, because the switches aren't all the same kind of thing. For the six ordinary ones the environment wins, and the control is shown disabled with the variable named beside it; a preference saved months ago mustn't quietly override something set deliberately for this launch, which is how a run ends up measuring a different code path than its reader believes. For the two that take a capability over your own machine, the event tap that swallows your keyboard and the input watcher, **off wins from either source and the control is never disabled**. An out-of-family review caught the first design failing exactly there: an environment variable could arm the keyboard tap, and the lock rule then greyed out the only control that could turn it off. So the person whose keyboard was being eaten was shown a switch they couldn't press.

  Seven of the eight take effect when the agent next starts, which the window says on the row rather than leaving you to find out. A saved change shows a pending marker and offers **Restart agent**, and the marker clears when the agent's own next report says the new value is what it's running with. Proctor never claims a change landed on the strength of having written it. The run panel is the exception; it already had a live show and hide, and it keeps it.

  Two of the controls are consent gates rather than checkboxes, with the disclosure above the control and a second press to turn them on. One click turns either off, and that asymmetry is the point. The second browser lane names an autonomous agent that drives a real browser with your real logins, and nothing it does reaches Proctor's audit trail; holding the keyboard and mouse takes your machine away from you while a step runs.

  Note: settings are saved in Proctor's own support folder, not in the launchd job. `scripts/install.sh` rewrites that plist wholesale every time it runs and writes no environment block at all, so a preference stored there would be destroyed by the next upgrade, silently, taking your settings with it. Worth being plain about the file that replaced it: any program running as you can write it, so it's a convenience for a person rather than a lock on a program. The window says so too.
- **`proctor_doctor` now knows the whole toolchain.** It used to report Proctor's own grants and two browser tools. It now reports everything Proctor leans on but doesn't ship: **Obscura**, **simctl** and Xcode, **cua-driver**, and **Maestro**. Each row says where the tool was found, everywhere it was looked for, whether it's usable, and what established that. A new **lanes** block says what this Mac can actually do (`mac`, `browser`, `ios`, `cua`), each with a three-state verdict and a fail-closed boolean, so a caller finds out there's no iOS lane here before it tries to use one rather than after. A new **policy** block reports the gate's posture: its mode, how big its lists are, whether an approval token is live, and whether the audit trail is writable and verifying clean.

  The health check runs none of those tools. Everything in it comes from a read: a stat, a readlink, one property list, and a code-signature check that reads the file and executes nothing. That's measured rather than squeamish. Asking Maestro for its version costs 3.9 to 5.3 seconds because it starts a JVM, and the status window asks for a health report every 2 seconds; reading the version out of Homebrew's symlink target costs nothing and gives the same answer, 2.4.0 either way. Xcode's version comes out of a root-owned plist the same way.

  So "installed" and "usable" are now two different things, with three states rather than two: **usable**, **unusable**, **unconfirmed**. Those are the same three the permissions already use, and `unconfirmed` means the same thing here it does there; it's a fact about what Proctor established, not about the tool. Every row also says which evidence backs its verdict, so it never claims more than it knows. `cua-driver` is the interesting one, because its daemon, its version and its own permissions are all invisible to a stat. The strongest thing a read can establish about it is its code signature, which happens to be exactly the check that decides whether Proctor will ever run it; a properly signed driver reads as `unconfirmed` rather than working, and an ad-hoc or wrongly signed one reads as `unusable`, with the same reason the lane itself would refuse for.

  Nothing another program printed reaches the report. `proctor_doctor` is the first call the Proctor skill tells a model to make, which makes it the worst place in the system to pipe another process's prose into. What gets reported about the delegated lane is only what Proctor produced or parsed itself: a version its own parser accepted, the stage of its own ordered checks that refused, and a permission map filtered down to the names Proctor recognises. Keys included, since those come from the other program too. The **policy** block holds a similar line and reports posture rather than rules, so no bundle id, no path, no key and no token. Note: that's a convention rather than a boundary, and it says so in place, because `proctor_policy` still answers in full to anybody who asks it.

  `scripts/doctor.sh` knows the toolchain now as well, and reports where it honestly disagrees with the agent. A launchd agent inherits no login shell's `PATH`, so a tool your terminal finds can be invisible to Proctor; that's the failure that produces "but it *is* installed". The script runs in your shell, it knows both answers, and it tells you which is which. Its search order is generated from the one Swift definition rather than typed out a second time in shell, and a test fails the build the moment the two drift.
- **A delegated action is still gated, and the trail says what it actually knows.** Proctor can now hand actuation to an external driver process (off by default). Every row of the audit trail used to rest on an assumption that quietly stops holding under delegation: that the process writing the record is the process performing the action. Left alone, the trail would have become a record of what Proctor asked for while keeping exactly the same words.

  A delegated row now carries three facts and keeps them apart. Which backend acted. What the driver claimed, meaning how it says it delivered the step and how confident it is that the step landed. And Proctor's own reading of the window's accessibility tree, taken before and after. The third one is the point; it's the only part Proctor witnessed. Where the driver's claim and Proctor's reading disagree, the row records the disagreement instead of picking a winner.

  There's also a new outcome, **indeterminate**, and it's deliberately not `failed`. Saying failed asserts the action didn't happen. When a driver dies mid-step or misses its deadline, the request may well have been delivered and performed before it went, and Proctor has no way to know. Those rows say so, and carry Proctor's own before and after reading as the only evidence left. History draws them as their own state, and the wording drops to "Press" rather than "Pressed", so Proctor never asserts in its own voice something it couldn't establish.

  A delegated call now has a real deadline; before this it could hang a step, a batch and the run panel indefinitely. A driver that misses it has its lane closed rather than reused, because the protocol matches replies to requests by position, so a late reply would be read as the answer to the next call. The lane itself is recorded too: opened (with the driver's path, its version, and where the transport allows it the identity of the running process), refused, build changed, died, timed out.

  Note: nothing recorded about the target widened. No new field carries an address, a window title, a typed value or caller text. And one thing worth stating plainly rather than leaving implied; the gate governs what Proctor does, not what happens to the machine. Any process with a shell can drive the driver directly, ungated and unlogged. Proctor can't prevent that and doesn't pretend to.

- **Proctor now has a history you can read.** The trail was already there, sealed and signed, and readable only by a tool. There's now a **History** window, from the menu bar or the Show history button on the status window's Activity card, showing what Proctor did on this Mac as one row per **run** rather than a line per event. Open a row and its steps unfold: Proctor's own past-tense wording for each one, the thing it acted on, which plane the action travelled, what came back, and how long it took. That object is drawn in a bordered chip, because the text in it is an application's own accessibility label; on a page of forty rows, one of them dressed up to look like Proctor's own words is a real thing to guard against, and a border is a fence no character inside the text can climb.

  The window never sees the trail itself. The agent holds the key, opens the trail, and hands back only the fields a row draws; the redacted fingerprints of typed values, the post-state hashes, the key ids and the internal session handles all stay in the agent. It decrypts only when a person opens the window, never on a poll, and the window is excluded from screen capture including Proctor's own `proctor_capture`. Neither history verb is in the tool catalogue, so no MCP host can read a person's history or clear it. That last point is narrower than it sounds and worth saying plainly: `proctor_policy` action `audit` already returns whole trail records to any host, and this projection is simply narrower than that one.

  Note: the history is now bounded, and it is not a sliding window. Proctor keeps **14 days or 10,000 entries**, whichever comes first, adjustable through `PROCTOR_HISTORY_DAYS` and `PROCTOR_HISTORY_ENTRIES` within a clamped range of 1 to 90 days and 100 to 100,000 entries. There is deliberately no value meaning keep everything. Passing either cap starts the record again rather than trimming the front of it, because the trail is hash chained and a trimmed front reads to the verifier as tampering rather than as housekeeping. What replaces it is a single record saying how many entries went, the span they covered, which trail they belonged to and the hash of its final entry, so a gap in the history is attested rather than silent. **Clear** is the same operation on demand and asks first. The window shows how much is held and how much of the window is left, so the day it starts again isn't a surprise. Each recorded action now also carries which run it belonged to, where it sat in that run, its elapsed time and its plane.

- **Every build now says which build it is.** The agent's version was a hardcoded `0.1.0` that had never been bumped, so two Macs running builds months apart reported the same string from `proctor_doctor` and there was no way to tell them apart. The identity is now generated when the build happens, and it carries five parts: the release line (read from the app's `Info.plist`), the exact short commit, whether uncommitted changes were in the build, whether it's a debug or a release build, and when that executable's file was written. `agentVersion` now reads like `0.1.0+e1f6cbf4fd1c`, picking up `.dirty` or `.debug` when they apply, and a new `agentBuild` object carries the same parts separately for anything that wants a field rather than a string. It works on a plain `swift build` and not only in the release workflow, so a developer's Mac reports its real build instead of a placeholder; outside a git checkout it says `unknown` rather than going empty. The status window shows the window's own build next to the agent's, so an upgrade that left the two halves of one bundle on different builds is something you can read rather than something you have to work out from file timestamps. The release workflow also checks that the git tag, the app version and the CHANGELOG section agree before it builds anything.
- **An installed web app is an app, not a browser tab.** A site you installed as a Mac app (Chrome, Edge and Brave's "install as app", Safari's "add to dock") gets its own bundle id, and Proctor used to read that as plain Chrome and tell a model to hand the page to a browser tool. That opens the same site in a different engine with an empty cookie jar and fails at a login wall, because people install a site as an app precisely because they use it signed in. Proctor now recognises one, names no browser tool for it, and drives it as an application the way it already drives Slack or VS Code. It still reports the address, so a caller who disagrees isn't left guessing, and it still keeps the advice about the page itself: a PDF or a local file in one of these windows gets the same answer it would anywhere else. Channel builds are covered too, so a web app installed from Chrome Canary, Edge Dev or Brave Beta is recognised as a web app rather than as a release channel.
- **Two machine-readable fields on every browser handoff.** `surface` says whether this is a browser window or an installed web app, which is what tells "no tool should touch this" apart from "Proctor drives this one itself". `flags` is five booleans where true means the fact is present: `actsOutsideThisWindow`, `autonomous`, `canActAsThisPerson`, `outsideTheAuditTrail`, `billed`. They describe whichever instrument the handoff points at, Proctor included when it is the one driving, so a host that refuses anything able to act with somebody's live browser session can gate on a field instead of parsing English. The prose all stays; the flags are the part a machine reads, and they carry nothing the prose doesn't say. One caveat worth stating: they describe what Proctor recommends, not everything a caller could do, so a policy that nothing may act in a live browser session should gate on the handoff being there at all. Internally, whether a browser is Chromium is now derived from the one scheme namespace each browser owns rather than stored as a second fact beside its name.
- **A hold says whose run it is.** When Proctor gets out of your way because you have taken the machine back, the hold now names the session that noticed, the application that run was driving, and which display that application is on. The session name is derived from the connecting client's own process and is never something a client can tell Proctor about itself, because a connection that could name itself could impersonate another one in the very panel you use to decide whether to stop it. The menu bar icon still shows precedence and nothing else, because one glyph cannot carry a name. The name goes on the run panel's queue bar, in the menu bar's text, and in `proctor_doctor`, which now marks each active run held with the reason behind it.
- **`proctor_apps.activate` takes its turn in the queue.** Bringing an application to the front changes where everybody else's clicks land, so activate now queues like every other run that takes the foreground. It can wait, and it can come back saying the machine was busy or that a person dropped it from the queue. Entries cut from the end, and a trail rolled back to an older copy of itself, are caught against a mark of how far the trail had got, which lives in the protected key store rather than in a file next to the trail; a marker on disk gets restored along with the trail from any snapshot, and the restored pair then verifies perfectly. An entry that can't be signed is dropped rather than written unsigned, because an unsigned entry couldn't be told apart from a forged one. Entries written before this change are reported as predating it, neither clean nor forged, and the first signed entry pins that older history, so an edit to it after today shows up. `proctor_policy` status and the audit tail now carry `auditVerdict`: whether the trail is clean, how many entries verified, how many predate signing, and the first fault with its position. What this doesn't claim is worth stating plainly. Anything running as this user on this Mac can ask the key to sign, exactly as Proctor does, so an agent that can sign can sign a lie it was told to write. The claim is narrower and it's the useful one: a clean verdict can't be manufactured anywhere other than here. Detection, not prevention.
- **The trail records that Proctor recommended a browser lane.** Proctor tells a model which browser tool should own a page and never drives one itself, so nothing either tool does reaches the trail. The recommendation is Proctor's own act though, and until now there was no record it happened. The trail now records which lane was named, which rule chose it, and the scheme of the address, once per browser per run rather than on every advisory that carries it. It records nothing else about the page: no address, no host, no path, no query, no fragment. A URL in an audit entry is somebody's browsing history in a file Proctor keeps, so the recorded facts are the ones the decision was actually made on and stop there. A redacted address was considered and dropped, and the reason generalises: length plus a hash is safe for a password because a password can't be guessed, and an address can, so anyone holding a list of candidate addresses could match it back.
- **Proctor can drive an iOS app now, by opening the URL that puts it where you want it.** A new `proctor_ios` tool lists the simulators on this machine, boots one when you ask it to, opens a deep link on a booted device, and screenshots the device surface. What matters is what the result tells you. `xcrun simctl openurl` exits zero when the URL was delivered, which isn't the same as the app going anywhere; run the same link twice and both calls exit zero while only the first one moves the screen. So `open` reports three channels separately (what simctl said, whether the target app's process is running, and a before-and-after comparison of the device screen) and picks a verdict that never claims more than those support: `targetChanged` when the app is running and the screen moved, `screenChanged` when something moved but it can't be pinned on the app the URL named, `deliveredOnly` when nothing observable happened, plus `deliveredUnobserved`, `targetGone` and `refused`. `deliveredOnly` is reported as inconclusive rather than a failure, because a link to the screen you're already on looks exactly like a link the app ignored. Note: a device handle is not a window handle, and every window-taking tool refuses one by name. The Mac's accessibility API doesn't reach into a simulated device, so an iOS app has no tree, no elements and no geometry assertions; the device screenshot is real, but it carries no ScreenCaptureKit frame status, so it comes back marked untrustworthy rather than borrowing a window capture's credibility. Proctor never boots a simulator as a side effect of opening a URL, and never shuts one down. The policy gate judges the app the URL actually resolves to on the device rather than a name the caller passed in, and iOS targets are named `ios:<bundleId>` in an allow list, so a Mac app on that list doesn't quietly authorise its iOS namesake. `proctor_doctor` gains a `simctl` row, so a machine without Xcode says so up front instead of failing when you reach for it.

- **Actuation now sits behind a swappable backend, and Cua Driver is the second one.** Everything that clicks, types, scrolls and picks a menu item used to be Proctor's own code and only Proctor's own code. It now goes through one seam, with Proctor's accessibility and synthetic-event planes on one side of it and `cua-driver` on the other. Observation deliberately did not move: Proctor still takes its own screenshots and walks its own accessibility tree, because Cua's screenshots carry no frame-status metadata and its own documentation says the tree lies on some surfaces, and a layer that exists to catch other people's silent failures needs at least one channel it can trust. The new lane is off unless you ask for it with `PROCTOR_ACTUATION=cua`, and Proctor never installs `cua-driver` for you.

- **A step can now say it was delivered in a way that needed no foreground, and can say it does not know.** `plane` grew two values. `routedEvent` is an injected event delivered to one process rather than to the shared event stream, which is background-safe and is not the accessibility plane, so neither of the existing words was true of it. `unknown` is a step that ran through a delivery mode this build does not recognise, and a run holding one is never described as background-safe: the sentence a caller reads changes, rather than a new field appearing that nothing reads. The driver's own word for how it delivered the step travels beside the mapped value, so you can audit the mapping instead of trusting it.

- **`scripts/test.sh`, a test gate that reports the real verdict.** Three ways a red suite reads as green, all of them measured on this repo: `swift test` piped into anything loses its exit code unless `pipefail` is set, so a check reading `$?` after `swift test | tail` sees `tail` succeed; the XCTest summary prints `Executed 0 tests, with 0 failures` on failing runs too, because the tests are swift-testing and that line counts the XCTest ones; and a filter matching nothing produces a real verdict line reading `Test run with 0 tests ... passed`. The script refuses all three, and says why in its own header so the rule lives next to the code rather than in somebody's memory.

### Changed

- **Proctor's own actuation planes stay, and the default stays with them.** Proctor recently gained the ability to hand actuation to an external driver process, off by default. The obvious next question was whether its own code should go now that a replacement exists. It shouldn't. An operator picks the delegated lane deliberately with an environment variable, and nothing ever falls back from one to the other on its own.

  Three reasons decided it, and any one of them was enough on its own. Proctor's own code covers 22 kinds of step across four routes, and the driver replaces two of them; it has no equivalent for running an application's own AppleScript, or for running a Shortcut, so deleting would have deleted two published verbs. The driver returns only a menu bar for a window on another desktop, where Proctor's retained references keep working, so the delegated lane can't drive windows the native one can. And `cua-driver` isn't installed on this machine and has never run here, so delegation is argued rather than exercised. Deleting a path that works, in favour of one that has never run once, isn't a trade worth making.

  Automatic fallback was refused on principle. For a tool whose output is a repeatability verdict, a run that quietly changes how it reaches the machine hands back a number that looks fine and measures the plumbing. Failing loudly beats a corrupted answer.

  What actually changed in the product: **every run record now names the actuation lane that produced it**, on the act result, the replay result and the repeatability report. It's there even when no step actuated at all, which is exactly the run you most want to place, because those steps carry no lane of their own to infer from. A repeatability verdict can no longer be read without the path it was measured on sitting beside it. One guard was tightened as well; replaying a recorded flow on a different lane from the one that recorded it was already refused, but the check only compared the first recorded step, so a recording whose opening step agreed and whose later steps didn't would have replayed. It now checks every step.

  Note: Proctor can make the actuation path impossible to leave off a verdict; it can't stop a person comparing two verdicts that were measured on different paths. And there's deliberately no condition that flips the default on its own. A default that moves when some condition becomes true would contaminate a score across runs the same way a mid-run fallback contaminates one within a run, and nobody would have chosen it. Moving the default would be a release that says so.
- **The status window's checks now say what they can actually check.** Permissions and tools were sharing one list, so the Shortcuts CLI rendered under "Optional, asked for per app", which is Automation's line and wrong for a command line tool. Tools have their own section now: Obscura, simctl with its Xcode version, cua-driver, Maestro and the Shortcuts CLI, each saying whether it's usable, what that verdict rests on, and behind a **Details** toggle, Proctor's own sentence about it plus every path it looked in. Those paths are there because a launchd agent inherits no login shell's `PATH`, so "but it *is* installed" is only ever settled by comparing where each side looked.

  Each permission now says what would move its answer, and that isn't the same for all three. Accessibility is read fresh every time, so Proctor picks up a grant you make in Settings on its own within a couple of seconds. A denied Screen Recording answer is settled by macOS when the agent starts and repeated for the life of that process, so it won't change in the window however many times anything re-reads it; only restarting the agent asks again. A Screen Recording probe that didn't come back is retried on its own and isn't a refusal. The restart offer that already existed in the menu bar now sits next to the permission it's about as well, reason and button together, and still only when the window can see the grant for itself, so a Mac that never granted Screen Recording gets no permanent prompt it can't act on.

  The footer's **Re-check** button is gone, and that's the measured part. The window already asks for a report every 2 seconds for its whole life, and the timestamp beside that button already advanced on its own, so the button refreshed rows that were refreshing themselves, next to a clock that was ticking anyway. The one row anybody pressed it for, a frozen Screen Recording denial, could never move. **Restart agent**, which can, is still there. The other two Re-check buttons stay, because each sits under an instruction it can genuinely confirm: one after starting the agent, one after running Obscura's install commands. The timestamp itself now says the report was asked for at that time rather than that everything in the window was checked then, because not every answer in it ages at the same rate.

- **A layout assertion that says "left-aligned" now means it.** `proctor_assert`'s `horizontalAlignment` kind tells you whether an element sits left, centre or right inside its container (a container node or rectangle you name, or the window frame when you name none). It shipped with several decisions that quietly weakened it, and this replaces them. The tolerance you pass is now one distance applied to all three placements; it used to be tripled for the two edges and left alone for the centre, so an element 24pt out of line still reported `left` while the same drift on the centre reported `custom`. The default is 1.0pt, the same as every other geometry assertion on the tool, instead of 8.0; copying a tolerance from one assertion to the next used to change strictness eightfold with nothing saying so. It now accepts `left`, `leading`, `center`, `centre`, `right` and `trailing`, rather than an alias for leading and nothing at all for trailing, and it reports the physical word, because it compares screen coordinates and doesn't read layout direction. In a container barely wider than its element the nearest placement wins; centre used to win by precedence, so an element filling its row failed a `right` check it hadn't broken. Only a genuine tie comes back as unknown rather than wrong, which in practice means an element that fills its container, or two placements that describe it to within one screen pixel. Four answers that used to be given silently are now reported instead: a `container` you asked for that has no readable frame is no longer measured against the window in its place, a frame that arrives with a nonsense width is no longer classified from comparisons that quietly fail, an assertion with no `expected` no longer asserts `leading` on your behalf, and a failure names all three measured offsets, the tolerance it used, and the likely fix when the container fell back to the window.

- **"Re-check now" is gone from the menu.** The refresh it triggered already runs on a repeating 2-second timer for as long as Proctor is running, window open or closed, so the button advanced a read by about two seconds. For the one permission it was there for it advanced nothing: the agent reads Screen Recording by asking ScreenCaptureKit, macOS caches that answer for the life of the process, and re-asking the same long-lived agent gets the same denial every time. Only a restart clears it, which is why granting through Proctor's own dialog already restarts the agent. In its place the menu offers **Restart Agent**, but only when the window can see for itself the grant the agent is denying, so a Mac that hasn't granted Screen Recording never gets a button that can't help; it says so when a run is in flight, because the restart stops it. A wedged agent, which the menu had nothing to say about before, now gets **Start Agent**.
- **Screenshots now fit the vision ceiling by default.** An oversized frame gets downsampled by the vision API anyway, so the only real question was whether that shrink happens where the scale factor is measured and reported, or where it's invisible and every coordinate the model hands back is quietly offset from the real screen. `proctor_capture` normalises to roughly 1568px on the long edge and 1.15MP, and reports the exact factor as `normalization.scale`, so you map a coordinate back with `native = normalised / scale`. Pass `normalize: false` when you want native pixels for a pixel-plane assertion, or set `normalizeMaxLongEdge` and `normalizeMaxPixels` to match a provider's tile grid (768 for Gemini, where crossing a tile boundary by a few pixels can double the token cost).
- **`proctor_capture` and `proctor_zoom` take a format.** Pass `format` as `"png"` or `"jpeg"` and `quality` between 60 and 100. PNG stays the default because it's what keeps small UI text readable: on a 3456x2234 retina capture normalised to the vision ceiling, macOS Vision OCR recovered 94% of the native-resolution words from PNG, 91% at JPEG q85 and 78% at q50, and the count of words misread as a *different* real word (which a model will happily act on) rose from 11 to 20 to 66. Note: WebP would be the better lossy container here, but macOS ships no encoder for it, so treat JPEG as a way to archive a lot of frames rather than a way to read a UI.
- **A leaner tool catalogue, and the installer now suggests `--profile core`.** The catalogue is re-sent on every turn and survives context compaction, so it's a standing cost you pay before any work happens. `--profile full` advertises all nineteen tools at roughly 11.3k tokens; `--profile core` advertises the ten that actually drive a Mac (apps, snapshot, find, act, capture, zoom, wait, assert, menu, doctor) at roughly 6.8k. Widen to `--profile scripting` or `--profile full` when you need flows, policy, kill or the CUA adapters.
- **Quit means everything.** Quitting Proctor now stops the background agent as well as the window. Both come back at your next login.
- **Replaying a recording is now gated and logged like driving the app by hand.** A flow recorded when an app was allowed used to replay just fine after an operator blocked it, and not one of those steps reached the audit trail. Replay and `proctor_stability` now pass the same policy gate as `proctor_act`, judged on the app behind the window being driven right now rather than the one named in the recording, and a target with no resolvable bundle id is refused outright when an allow list is in force. Every replayed step is written individually, with typed text and script bodies reduced to length plus SHA-256 exactly as a live step is, and the trail names its driver so you can tell them apart: `proctor_act`, `proctor_flow.replay`, `proctor_stability.replay`, `proctor_stability.reset`. `proctor_stability` re-checks permission before each repeat, so a time-limited approval token genuinely expires mid-run; the run stops there, reports how many repeats it completed, and a truncated run is never reported deterministic. Note: recording, listing, showing and deleting a flow drive nothing, so they stay ungated.
- **The audit trail is encrypted at rest.** Every entry is sealed on its own to a key that lives in this Mac's login keychain, which is never synced and never backed up, so the log is unreadable if the file is copied off the machine, restored from a backup, or opened by another account. Writing doesn't need that key, only reading does, so an unattended run keeps recording between a restart and the first time anybody unlocks the Mac. An entry that can't be sealed is dropped rather than written readable, and `proctor_policy` status now reports `auditWritable` and a count of anything lost, where a failed write used to be silent. Note: a readable trail left by an earlier version is converted in place the first time the agent writes, all or nothing, and that removes the last readable copy of it; there's no recovery key and no export, so losing the keychain key means losing the history. What it doesn't claim: hiding how many entries there are or when they happened, spotting a deleted or forged entry, or keeping out a program already running as you.

- **A driver that reports success is not a machine that moved.** When `cua-driver` says it suspects a step did nothing and Proctor's own reading of the window after that step agrees nothing changed, the step fails instead of reporting success. Two independent observers have to agree before that verdict lands; a suspected no-op the window contradicts stays a pass and carries the suspicion beside it.

- **Elements cross the boundary by what they are, never by where they are.** A target is matched into the driver's view through its role and label ancestry, and a candidate set that only a coordinate could separate is refused rather than resolved, because a match resting on a position replays by striking an absolute point and breaks the moment a layout moves. Both sides have to agree about the element before anything is struck, which is what catches a window that changed between the look and the click. A target that moved, is ambiguous, cannot be seen, or sits on another Space is refused with the reason named, and no coordinate is ever substituted for an element that failed to resolve.

- **The driver is checked before it is ever run.** Presence is read off the filesystem and executes nothing, as it always has. Selecting the lane then checks the binary's code signature against a pinned identity and its version against a supported range, and refuses clearly on either, naming what was found and what is supported rather than failing at the first call with a schema error. Both refusals have an override for people who know what they are doing, and taking one stamps every record the run produces. A build reporting delivery modes this Proctor cannot map is refused at the same gate.

- **A flow recorded on one backend will not replay or be scored on another.** A divergence between a recording and a replay that used different actuation paths measures the paths, not the application under test, so Proctor refuses the comparison rather than publishing a number that means something else. Flows recorded before this change carry no backend and replay exactly as they did.

### Fixed

- **Proctor opens when you open it, even while its agent is running.** The agent is a second executable inside the app bundle, started by launchd, and macOS had been recording it as a running copy of Proctor itself. So `open -a Proctor`, and double-clicking Proctor in `/Applications`, activated a process that has no window and then reported success. Nothing appeared and there was no error to read; the installer's final "opening Proctor" step was a silent no-op on every reinstall. The agent now declares an identity of its own to LaunchServices, so opening Proctor opens Proctor. Its code signature is deliberately unchanged, which is what keeps your existing Accessibility and Screen Recording grants working across the upgrade instead of asking you for them again, and the build now refuses to produce an app where either of those two properties has broken.

- **`proctor_doctor` can no longer hang on its own first question.** It reads the Screen Recording grant by asking ScreenCaptureKit for shareable content, and the code assumed that call either answers or throws. Measured on 15 August it did neither; it parked and never came back, while the same call from a plain script on the same Mac answered in 0.037 seconds. `proctor_doctor` is the first call the Proctor skill tells a model to make, so a campaign could stall on its opening move with nothing to read. The probe is now bounded at 1.5 seconds, and a grant macOS did not answer for reports a third state, `unconfirmed`, rather than borrowing the word for a denial. That distinction is the whole point: calling it denied sends somebody to System Settings to grant a permission they may already have granted. Every entry in `grants` now carries `state` (`granted`, `denied` or `unconfirmed`) beside the existing `granted` boolean, which now means confirmed granted and stays false for the other two, so nothing that reads only the boolean over-claims. `ready` is false while a required grant is unconfirmed, because ready means established-good. The remedy text names the bound and says to call `proctor_doctor` again or restart the agent, instead of pointing at System Settings; the status window drops its **Open Settings** button for an unconfirmed grant, and the menu bar shows its own symbol rather than the missing-permission triangle, which would be reporting a fault the machine has not been shown to have. A definite answer is cached for the life of the agent, which is how macOS caches it per process anyway; a non-answer never is, because it is a property of the moment rather than of the process, and remembering one would leave the agent giving that same non-answer for the rest of its life. If the abandoned probe does eventually come back, the next call picks its answer up. Note: the full test suite runs unskipped again; two suites had been skipped for two waves because six tests hung on this same call.

- **Stop stays clickable while Proctor is driving.** The run panel has to get out of the way when Proctor posts a click, or Proctor's own click lands on the panel instead of the app underneath. That used to mean the whole panel went click-through for the whole of every such step, so a person reaching for Stop clicked straight through it into the app being driven. The kill switch was dead, and the same gesture disturbed the run it was meant to end. Now the panel only steps aside when the step is about to post an event, and to post it where the panel is standing, so everywhere else Stop works right through the step. The new rule also covers a scroll or a keystroke that quietly falls back to a synthetic event, which the old one missed because it went by the step's type rather than by what the step actually did, and the panel comes back the moment the step settles rather than staying transparent until the next step starts. If you have turned on the optional input hold with `PROCTOR_TAKEOVER_INPUT`, a click on Stop now ends the run on the first press instead of the second. Proctor's own clicks still cannot press Stop, and that is enforced twice over. One case is unchanged and worth knowing: with the input hold off and a step posting into the panel's own corner, that click still reaches the app underneath.

- **A hold now stops only the run that noticed it.** One shared latch used to park every run in flight, so an accessibility-only run in another session driving a different application would stop dead for up to fifteen minutes with nothing said to anyone about why. The automatic hold belongs to the run that read the contention. A person's Pause still holds everything, because that is a decision about the machine rather than a reading about one event stream.
- **A run starting no longer lifts another run's hold.** The scheduler never consulted the halt latch, so any run beginning on a free lane cleared a live hold along with its clock and its limit, and the held run carried on posting into the person it had just got out of the way of.
- **An expired hold gives up on one run instead of all of them.** When the fifteen-minute limit runs out on an automatic hold it now ends that run alone. It used to stop every run that was going at the time and tell each caller that a person had stopped it from the run HUD, which is a halt nobody chose reported as somebody's decision.
- **The window shows the permissions you have already granted.** A name mismatch between the window and the agent meant every check read as "agent not answering", even with both grants in place. The window reads the agent correctly now, and reflects a grant within a couple of seconds of you making it. Granting Screen Recording restarts the agent for you, so it stops asking for a permission you just gave.
- **Secure Event Input no longer wears the missing-permission warning.** Proctor's menu bar shows the character when it can work and a status symbol when it can't, and the symbol for "a permission is missing" was also being shown whenever Secure Event Input was active. That happens every time a password field takes focus, and for as long as Terminal has Secure Keyboard Entry switched on, so a Mac with every grant in place was wearing a permission warning several times a day. It has its own symbol now, a locked laptop, rather than the warning triangle. It still takes the character off the menu bar, because clicks and keystrokes really are dead while it's on and that's worth knowing before you start a run rather than four steps into one. A missing permission outranks it when both are true. Note: `proctor_doctor` is unchanged. It still reports `secureEventInputActive` and still lists it as a blocker, because a model asking whether every plane will work needs that answer, and the menu bar is asking a narrower question.
- **A menu bar picture that won't load no longer reports success.** When the character's art couldn't be decoded, the menu bar fell back to a checkmark seal, which reads as everything being fine. That same seal was also what Proctor showed for ready before the character existed, so one picture meant three different things at once and a stale menu bar looked exactly like a broken readiness rule. The fallback is a question mark circle now, which appears nowhere else.

- **The takeover statement now holds up when more than one run is in flight.** A run that could never send synthetic events was still driving the shared declaration state, and it cleared that state underneath whichever run actually was posting. Two things went wrong when it did: the posting run stopped raising the on-screen statement that says Proctor has taken the machine, so nobody was told; and the event tap's in-flight window closed early, which put it back to reading the Stop button while Proctor's own click was still travelling. Only a run that can post touches that state now, and because such a run holds the exclusive global lane, it has that state to itself.

## [0.1.0] - 2026-08-14

First public release.

### Added

- **Computer use over MCP.** Any MCP-speaking model can drive this Mac: read the screen, find controls, click, type, scroll, and check that what it did actually landed. Nineteen tools in all, from `attach` and `snapshot` through `find`, `act`, `capture`, `zoom`, `wait` and `assert` to `flow`, `stability`, `inspect` and `doctor`.
- **A real UI-testing harness, not just a driver.** `assert`, `wait`, `stability` and `flow` turn the same tools into acceptance checks: wait for a window to settle, assert an element is there, replay a sequence, and get told when the screen is still moving.
- **Windows in the background stay in the background.** Proctor drives occluded windows, minimised windows, and windows on another Space without pulling focus or stealing your pointer, working across the accessibility and Apple Events planes rather than faking clicks at the front.
- **Screenshots that tell you how old they are.** Captures come back through ScreenCaptureKit with freshness metadata, so a model acting on a frame knows whether it is looking at now or at a moment ago.
- **Grants that survive an upgrade.** Accessibility and Screen Recording are granted once to a stable launchd-agent identity keyed to the Developer ID signature, not to a path or a build, so a reinstall or a version bump does not send you back to System Settings.
- **The tools every model already knows.** Stock Anthropic and OpenAI computer-use schema façades sit over the native tools, so a model trained on either can attach with no custom wiring.
- **Menus, dictionary, a policy gate, and a redacting audit log.** Read menu bars, look words up, gate actions behind a policy, and keep an audit trail that redacts what it should not record. Plus process kill and screen unlock for the moments automation gets stuck.
- **Signed, notarised, and installed properly.** The first public build ships as a notarised Developer ID release into `/Applications`, run as a per-user launchd agent.
