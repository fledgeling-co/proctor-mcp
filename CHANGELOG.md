# Changelog

All notable changes to Proctor are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Proctor now has a history you can read.** The trail was already there, sealed and signed, and readable only by a tool. There's now a **History** window, from the menu bar or the Show history button on the status window's Activity card, showing what Proctor did on this Mac as one row per **run** rather than a line per event. Open a row and its steps unfold: Proctor's own past-tense wording for each one, the thing it acted on, which plane the action travelled, what came back, and how long it took. That object is drawn in a bordered chip, because the text in it is an application's own accessibility label; on a page of forty rows, one of them dressed up to look like Proctor's own words is a real thing to guard against, and a border is a fence no character inside the text can climb.

  The window never sees the trail itself. The agent holds the key, opens the trail, and hands back only the fields a row draws; the redacted fingerprints of typed values, the post-state hashes, the key ids and the internal session handles all stay in the agent. It decrypts only when a person opens the window, never on a poll, and the window is excluded from screen capture including Proctor's own `proctor_capture`. Neither history verb is in the tool catalogue, so no MCP host can read a person's history or clear it. That last point is narrower than it sounds and worth saying plainly: `proctor_policy` action `audit` already returns whole trail records to any host, and this projection is simply narrower than that one.

  Note: the history is now bounded, and it is not a sliding window. Proctor keeps **14 days or 10,000 entries**, whichever comes first, adjustable through `PROCTOR_HISTORY_DAYS` and `PROCTOR_HISTORY_ENTRIES` within a clamped range of 1 to 90 days and 100 to 100,000 entries. There is deliberately no value meaning keep everything. Passing either cap starts the record again rather than trimming the front of it, because the trail is hash chained and a trimmed front reads to the verifier as tampering rather than as housekeeping. What replaces it is a single record saying how many entries went, the span they covered, which trail they belonged to and the hash of its final entry, so a gap in the history is attested rather than silent. **Clear** is the same operation on demand and asks first. The window shows how much is held and how much of the window is left, so the day it starts again isn't a surprise. Each recorded action now also carries which run it belonged to, where it sat in that run, its elapsed time and its plane.

- **Every build now says which build it is.** The agent's version was a hardcoded `0.1.0` that had never been bumped, so two Macs running builds months apart reported the same string from `proctor_doctor` and there was no way to tell them apart. The identity is now generated when the build happens, and it carries five parts: the release line (read from the app's `Info.plist`), the exact short commit, whether uncommitted changes were in the build, whether it's a debug or a release build, and when that executable's file was written. `agentVersion` now reads like `0.1.0+e1f6cbf4fd1c`, picking up `.dirty` or `.debug` when they apply, and a new `agentBuild` object carries the same parts separately for anything that wants a field rather than a string. It works on a plain `swift build` and not only in the release workflow, so a developer's Mac reports its real build instead of a placeholder; outside a git checkout it says `unknown` rather than going empty. The status window shows the window's own build next to the agent's, so an upgrade that left the two halves of one bundle on different builds is something you can read rather than something you have to work out from file timestamps. The release workflow also checks that the git tag, the app version and the CHANGELOG section agree before it builds anything.
- **An installed web app is an app, not a browser tab.** A site you installed as a Mac app (Chrome, Edge and Brave's "install as app", Safari's "add to dock") gets its own bundle id, and Proctor used to read that as plain Chrome and tell a model to hand the page to a browser tool. That opens the same site in a different engine with an empty cookie jar and fails at a login wall, because people install a site as an app precisely because they use it signed in. Proctor now recognises one, names no browser tool for it, and drives it as an application the way it already drives Slack or VS Code. It still reports the address, so a caller who disagrees isn't left guessing, and it still keeps the advice about the page itself: a PDF or a local file in one of these windows gets the same answer it would anywhere else. Channel builds are covered too, so a web app installed from Chrome Canary, Edge Dev or Brave Beta is recognised as a web app rather than as a release channel.
- **Two machine-readable fields on every browser handoff.** `surface` says whether this is a browser window or an installed web app, which is what tells "no tool should touch this" apart from "Proctor drives this one itself". `flags` is five booleans where true means the fact is present: `actsOutsideThisWindow`, `autonomous`, `canActAsThisPerson`, `outsideTheAuditTrail`, `billed`. They describe whichever instrument the handoff points at, Proctor included when it is the one driving, so a host that refuses anything able to act with somebody's live browser session can gate on a field instead of parsing English. The prose all stays; the flags are the part a machine reads, and they carry nothing the prose doesn't say. One caveat worth stating: they describe what Proctor recommends, not everything a caller could do, so a policy that nothing may act in a live browser session should gate on the handoff being there at all. Internally, whether a browser is Chromium is now derived from the one scheme namespace each browser owns rather than stored as a second fact beside its name.
- **A hold says whose run it is.** When Proctor gets out of your way because you have taken the machine back, the hold now names the session that noticed, the application that run was driving, and which display that application is on. The session name is derived from the connecting client's own process and is never something a client can tell Proctor about itself, because a connection that could name itself could impersonate another one in the very panel you use to decide whether to stop it. The menu bar icon still shows precedence and nothing else, because one glyph cannot carry a name. The name goes on the run panel's queue bar, in the menu bar's text, and in `proctor_doctor`, which now marks each active run held with the reason behind it.
- **`proctor_apps.activate` takes its turn in the queue.** Bringing an application to the front changes where everybody else's clicks land, so activate now queues like every other run that takes the foreground. It can wait, and it can come back saying the machine was busy or that a person dropped it from the queue. Nothing is brought to the front on either path, so a busy-machine refusal is safe to send again and a person's is a reason to ask first.
- **A second browser lane, for the pages Obscura has no equivalent of.** Proctor tells a model which browser tool should own a page; it never drives one itself. Obscura is still the default, and now a page that lives inside the browser (`chrome://`, an extension page, a browser-internal scheme) can name the browser-use CLI instead, because Obscura's engine has no such page at all. Every handoff carries a `why` sentence naming the rule that chose the lane, so the advice is checkable. Two gates stand in front of it: `PROCTOR_SECOND_LANE=browser-use` in the agent's launchd environment decides whether the tool may be named at all (unset means Obscura only, which is the default), and finding the binary decides whether the lane is usable. Installing a CLI is consent to have a file; it isn't consent for a process holding Accessibility to name that file to a model with a shell. browser-use is an autonomous agent, its default mode drives a real browser with real credentials, and nothing it does reaches Proctor's audit trail, so the handoff says all three at both detail levels. It ships no command templates for that lane, only prose about which mode to run it in. Note: it's never a fallback when Obscura is missing, and it's never pointed at the browser's own settings, password manager, extensions, history or DevTools. `proctor_doctor` gains a `tools` array and a `secondLane` state.
- **A menu-bar icon that is always there, and starts with your Mac.** Proctor registers itself to launch at login and lives in the menu bar, so it is one click away without hunting for the app. The menu shows what it is doing right now: the tool it is running, the last one it ran, or that it is idle.
- **Onboarding that asks for both permissions on one screen.** First run is now a single sheet in the register of a system permission prompt: the two grants side by side, each with an Allow button that triggers the real macOS dialog, and the steps animate rather than jump. Motion respects Reduce Motion.
- **Proctor draws a pointer while it drives an app.** An accessibility press actuates a button with nothing moving on screen, which is exactly what lets a run work on a background window and exactly what makes it impossible to follow; somebody watching sees menus open and text appear with no cause. The pointer travels to each step's target before the step fires, leans into the direction it's travelling, and pulses where it acts. It draws one panel per display rather than one spanning them all, and that isn't a stylistic choice: a panel sized to the union of a 1728x1117 laptop and a 2560x1440 display is a 26-megapixel backing store that the window server accepts and reports as onscreen with alpha 1, and then never presents. Note: it never appears in a `proctor_capture`, because captures are window-scoped to the app under test, so it can't move a state hash or change a pixel assertion. Set `PROCTOR_CURSOR=0` to turn it off for an unattended suite, or for a machine somebody else is working on.
- **A panel that tells you what Proctor is doing, and a button that stops it.** A run used to be invisible unless you were watching the drawn pointer, and there was no way to halt one short of quitting the agent. A run now puts a small panel over the app it is driving: one line naming the step in flight, a step counter, a progress rail along the panel's own bottom edge, the last three steps with how long each took to settle, a run clock, and Pause and Stop. Pause holds before the next step and lets the one in flight finish settling, because killing a step halfway through leaves the app in a state nobody can describe; Stop ends the run there. A stopped run still reports the steps it completed, and attaches the refusal to the first step that never ran under its own code, `haltedByPerson`, so the model that asked can tell a person's decision from a policy rule or a broken app. Every kind of run shows it: a batch, a replayed flow, a stability sweep, and both computer-use façades. The panel is neutral graphite over whatever it floats above, with one colour carrying the state, and it follows your light or dark setting. Note: it needs the agent to run an application event loop, which it now does, and that is the one behavioural change worth knowing about; settling is unaffected, because the accessibility observers it depends on were already registered on the common run loop modes. A pause nobody resumes gives up after fifteen minutes and reports itself the way a stop does (`PROCTOR_HUD_PAUSE_LIMIT`, in seconds, to change that). Only the grip and the two buttons are live, so nothing else on the panel reacts to a click; a click on the body is discarded rather than handed to the app underneath, and the panel gets out of the way entirely while Proctor is posting a synthetic click, hover or drag, so a step aimed at a point under the panel still lands on the app. The panel is excluded from screen sharing and never appears in a `proctor_capture`, so watching a run cannot change its evidence. Set `PROCTOR_HUD=0` to turn it off for an unattended machine or one somebody else is using; it is separate from `PROCTOR_CURSOR`, so you can keep either without the other. `proctor_doctor` gains a `hud` block saying whether the panel is actually on screen, because believing you have a stop button you do not have is worse than knowing you have none. The character's bay is drawn and left empty, and the queue bar is not built yet; both arrive with their own changes.
- **The determinism run can now show you the step, not just score it.** `proctor_stability` replays a flow N times and tells you where the runs stopped agreeing, which is the right answer to "is this flaky" and a useless one when you want to see what step 7 actually looked like on the replay that diverged. Pass `captureEach` and every step that runs, in every replay, writes a PNG through the same step-running path that `act` and `flow` replay use, so the frames are genuinely per-step rather than N pictures of the end state. A replay that breaks mid-flow photographs the steps before the break and reports the rest as not attempted, rather than claiming a frame it never took. Pass `pointerMarks` as well and each frame gets a marker composited where that step acted. The report gains a `captures` ledger whose every entry names its replay index, its step index and its file locations, because a flat per-step list can't say which replay a frame came from and comparing one step across replays is the whole point. Both switches are off by default and the scoring is untouched: `firstDivergence`, `stepInstability`, `deterministic` and `divergenceDetail` are computed exactly as before. Note: capturing after every step moves the run's timings, so the report says so rather than letting a captured run's score be compared quietly against one taken without. Asking for `pointerMarks` with `captureEach` off turns capture on and tells you, rather than accepting a switch that does nothing. An opt-in run writes roughly runs × steps images, doubled where a marker is drawn, and nothing cleans them up. The marker annotates where the step acted and is not a live cursor; Proctor drives through the accessibility and Apple Events planes and doesn't move the system pointer. A step whose frame or marker couldn't be produced says so in the ledger, and doesn't fail the run or change its score.
- **Two sessions can now share a Mac without standing on each other.** Proctor is one agent behind one socket and any number of MCP clients can connect to it, and until now nothing arbitrated between them: two sessions driving the same machine interleaved their steps, and the second one's synthetic click landed in whatever window the first had just raised. The recorded step order in a test with the scheduler taken out is one, two, one, two, one, two, two, one, which is the failure exactly. There is now a scheduler, and it is three lanes rather than one queue, because queueing everything would make Proctor feel broken for the common case. Reads never join the line: `snapshot`, `find`, `capture`, `menu`, `zoom` and `assert` observe without mutating and run immediately, always. An accessibility press is IPC to one process, so two sessions driving different applications genuinely run in parallel; two on the same application take turns. A synthetic `click`, `hover`, `dragPath` or `key`, a batch that asked for `foreground`, and a `raise` step all take the whole machine, one at a time anywhere on it, because each of them changes what is in front and therefore where everybody else's clicks land. What queues is a whole batch, never a step: a six-step login is not split across two sessions' turns, and a stability sweep holds its lanes across every repeat rather than rejoining the line between them. Each session is named for the process on the other end of the socket, never for anything the client sends: its working directory gives the project and a four-character id separates two sessions in the same repo, so the panel prints `proctor-mcp a3f1`. A connection that could name itself could name itself as somebody else's project in the very UI a person uses to decide whose run to stop. A call that has to wait is held open until its turn instead of being answered with a position it would have to re-send, and gives up after forty-five seconds saying the machine was busy and where it stood (`PROCTOR_QUEUE_WAIT_LIMIT`, in seconds, to change that); a caller told nothing retries, and a retry behind a queue is how a queue becomes a stampede. One session may keep three runs waiting and a fourth is refused on the spot, so a session in a loop cannot starve the others. It is first come, first served within a lane, and a run that needs the whole machine becomes a barrier once it reaches the head of the line rather than being walked past forever. The run HUD gains an `N sessions waiting` bar between the step trail and the run controls, absent entirely when nothing is waiting, expanding in place to each run's position, session, what it wants and how long it has waited, with a drop control per row and Hold and Clear in the list header. Hold stops any waiting run starting, the active session's own next one included, and leaves the run in flight alone; Clear removes every waiting run and leaves the active one untouched. The queue's controls are Hold and Clear and the run's are Pause and Stop, never adjacent and never sharing a word, because two controls both called "pause" is how somebody stops the wrong thing. The menu bar mirrors the waiting count, so the queue is answerable without the panel on screen, and `proctor_doctor` gains a `queue` block reporting how many runs are active and waiting per lane, whether the queue is held, and how long each active hold has been held. Note: when a person clears the queue or drops a run, that caller's call comes back under `haltedByPerson` saying a person removed it rather than that a step failed, since one is a signal to stop and ask and the other a signal to retry; a refusal that is nobody's decision uses a new code, `queueBusy`, which always means nothing was actuated and the call is safe to send again. The permission gate is read a second time once a run's turn comes, so a time-limited approval that expired while the run waited refuses it rather than letting it drive on stale authority. A long sweep may hold its lanes for its whole length and only a person's Stop shortens it; the forty-five second ceiling caps how long anybody waits, never how long a run may take. And a waiting caller that has gone away cannot be seen to have gone from where the wait happens, so it keeps its place until its turn comes or the ceiling fires.
- **The run panel has a character in it now.** The bay at the left of the panel shipped empty; it now holds a small compact Mac whose screen changes with the run. Dot eyes while it waits, leaning with speed lines while it travels to a step's target, an orange screen while it presses something, a warning while blocked, grey pause bars while paused, a tick when the run finishes and a cross when it fails. The screen is what carries the state rather than a face or a pose, which is what keeps all seven readable at 38 points, and paused is the only grey one so it reads without relying on colour. Idle, travelling and acting move; the other four hold still. The loop is handed to the render server in one pass, so the agent never draws a frame of it while it is busy watching an app settle, which is the same reason the drawn pointer works that way. Note: Reduce Motion stops the character and the progress rail's pulse, and every state still reads from its screen alone, because that was the rule the character was drawn to in the first place. The art ships inside the app at standard, double and triple density, so nothing is fetched while a run is going, and a picture that will not load leaves the bay empty rather than stopping the run.
- **Proctor's menu bar can put the run panel away, and its icon is the character.** Switching the panel off used to mean `PROCTOR_HUD=0`, which means editing a launchd plist and reloading the agent; that's the wrong shape for something you want gone for ten minutes and back afterwards. **Show Run Panel** in the menu now hides and shows it at once, for the run in flight, and nothing is written to disk, so the environment is still the default at the next launch. Hiding the panel takes Pause and Stop off the screen, and the panel is the kill switch, so the menu carries **Pause/Resume** and **Stop** for as long as a run is live. Those are the run's words; Hold and Clear still belong to the queue and stay on the panel, because two controls both called "pause" is how somebody stops the wrong thing. The menu bar icon is the same compact Mac the panel draws, at 22 points, in the state the run is actually in: dot eyes while it waits, leaning while it travels, an orange screen while it presses, a warning while blocked, grey bars while paused, a tick when it finishes, a cross when it fails. One run state feeds both, so the menu bar and the panel can never disagree, and a glance at the top of the screen answers "what is Proctor doing" without finding a panel that may be on a display you aren't looking at. Note: 22 points rather than the usual 18 because 18 was rendered and rejected; the screen glyph collapses at that size and blocked and acting become the same solid block. It ships in full colour rather than as a template image, so it doesn't adopt menu bar tinting: vermilion carries acting, blocked, finished and error, and grey belongs to paused alone, and a template would throw all of that away. It's still when nothing is running and never moves under Reduce Motion. It also yields: if the agent isn't answering, or a permission it needs is missing, you get the status symbol instead, since a calm idle character over a Proctor that can't work is a picture telling you something untrue about your Mac. An agent started with `PROCTOR_HUD` off can't bring the panel back from the menu, because that launch runs no application event loop, so a panel drawn under it would have a Stop nobody could click; the menu says so rather than greying the item out silently. `proctor_doctor` now tells the four absences apart: switched off at launch, hidden from the menu bar with the controls still there, no event loop, and a drawing fault.
- **You can see a run coming before it takes your machine.** Proctor drives through the accessibility plane by default, which reaches background and other-Space windows without stealing focus, and that's the whole reason a suite can run while somebody is using the Mac. Some steps can't travel that way. A `click`, `hover`, `key` or `dragPath` enters the single system event stream and needs the app in front; a `type` or `scroll` usually goes through accessibility and falls back to the event stream when the element can't be written. Until now the only statement about any of that was one line on the run panel, during the step, on a panel that may well be on a display you aren't looking at. By the time it's readable the machine has already gone. The steps are known when the call arrives, so the panel now says so up front: **2 of 6 steps need Acme Console in front**, from the moment the run appears. It's stated as what the batch contains rather than as a prediction, because a batch can end before it reaches step two and it can't stop containing one. Where a `type` or `scroll` could add to that number the line says "at least" instead, and when one of them does fall back to the event stream the count revises upward as it happens. The **menu bar** mirrors it, so the fact reaches you on whichever display you're actually looking at, and its glyph changes while a step is genuinely being posted; that works with the panel switched off entirely. And `proctor_act` and a flow replay now return a **`foreground`** block: how many steps were known to need the front, how many might have, and how many actually travelled as synthetic events, measured from the planes the steps reported rather than predicted a second time. "This suite can't run unattended" is a field you can read rather than something you find out by watching. Note: nothing new is refused and no step changed plane; this is disclosure, not policy. The menu bar samples at its polling interval, so a synthetic step shorter than one poll can begin and end between two samples and never show up there. The panel is the instantaneous surface and the menu bar is the one that doesn't depend on which screen the panel landed on; neither replaces the other.
- **Proctor tells you when the thing it's driving is a web page.** Attaching to Chrome or Safari and walking the page's accessibility tree works, and it's the wrong instrument: it gives up the DOM, computed styles, the console, the network log and a selector that survives a re-render, in exchange for a flattened tree and a set of coordinates. A result whose target is a browser showing a page now carries a `browser` object naming Obscura as the tool for the page. It arrives on `proctor_apps` (both listing and attaching), `proctor_snapshot`, `proctor_find` and `proctor_act`; in full once, at attach, where the instrument actually gets chosen, and briefly everywhere else. It carries the page's URL when one is readable, and when one isn't it says which reason applies: no URL on the web area, several web areas at different URLs (Proctor won't pick one for you), or a scheme Obscura can't open at all such as `chrome://` or the built-in PDF viewer, where it drops the recommendation and keeps the disclosure. Nothing is refused and no step changes plane. The native chrome around the page (toolbar, tab bar, menus, sheets) stays Proctor's and is still yours to drive, so a click on the reload button doesn't get told to go and use something else. Note: a web view inside a native Mac app is not routed, because reaching it means attaching to the host process, which is exactly Proctor's job. Note: the command templates keep a literal `<url>` placeholder and the URL travels in its own field, because a page URL is text somebody else chose and splicing it into a command a model might paste into a shell is how that becomes a problem. Two things the object says out loud, since both are easy to get wrong. Obscura runs its own engine with its own cookie jar, so following the advice restarts at a URL rather than continuing that window's signed-in session; anything authenticated or multi-step has to be re-established there. And a step into page content still hashes, but over a browser's render tree rather than an app's view hierarchy, so a determinism score across a page measures the page's own churn as much as the app's. A local address carries the `--allow-private-network` caveat even in the brief form, because without that flag Obscura blocks the fetch and the failure reads like a network error. What this deliberately doesn't do is proxy steps through Obscura, or add a third actuation plane beside accessibility and synthetic events: Obscura drives its own engine and never the window Proctor is attached to, so a routed step would open a second unrelated page and report success against a window it never touched.
- **Proctor gets out of your way when you start using your own Mac.** A run that posts synthetic events holds the one system event stream your keyboard and mouse go into, so while it runs you're fighting it: you click, it clicks somewhere else. It now notices and holds the run instead of arguing with you. Three things count as you taking the machine back. The app Proctor brought to the front is no longer in front. Secure Event Input turned on, which means a password field somewhere has focus, and that's the one moment injected keystrokes are least welcome. And, only if you ask for it with `PROCTOR_YIELD_INPUT`, your own keystroke or click. Only a run that actually takes the foreground can be held; an accessibility-plane run never touches the front, so holding one would be noise about a contention that can't happen to it. The hold is the same pause a person's own Pause uses, with the same fifteen-minute backstop, so an automatic hold can never outlast the bound your own hold has. The panel says why in one line and **Resume** and **Stop** are its two answers; the menu bar mirrors it, so it reaches you on whichever display you're actually looking at. Pressing Resume overrides the condition that caused the hold, so the button isn't quietly undone on the next poll while you're still in another app. Left alone, the hold lifts by itself the moment the condition clears, after a short delay so one flicker of the front doesn't release a real hold. `proctor_act` and a flow replay return a **`yields`** block with the reason, the step, how long it was held and how it ended, so a suite that took four minutes because somebody was at the machine says so rather than looking slow. Note: the input observation ships **off**, and that's deliberate rather than cautious. An agent that already holds Accessibility shouldn't quietly pick up an input-observation capability nobody asked for, so what a default install gets is the two signals that read facts about the machine rather than watching what you did. Switched on, it exists only inside a run that is already contending, it's a passive observer that can't swallow or rewrite an event, and it records one timestamp: never a keycode, a character or a location. `PROCTOR_YIELD=0` turns the whole thing off. Note: Proctor's own events can't be read as yours, which matters because getting that wrong would pause every synthetic run on its own first click. Every event it posts carries its tag, its posts carry its own process id where real hardware carries none, and anything arriving within a quarter second of one of its own posts is discarded whatever it looks like. Note: the frontmost signal says what happened to the front, not who did it, so an app that launches a helper and loses focus to it reads as contention. That false positive is deliberately cheap, since nobody has to do anything about it: the app comes back to the front and the run carries on.
- **Proctor takes the background route wherever one exists, and the pointer stops floating over the app you're using.** Two complaints, one change. Asking for `foreground: true` used to be enough to take the machine, and for a batch of accessibility steps that was a promise Proctor never kept: nothing brings an app to the front except a synthetic event, so a run of presses and value writes took the exclusive scheduler lane, armed the yield watch and announced a takeover, then travelled the accessibility plane and left your Mac alone. A request no step in the batch could use is now ignored, and the `foreground` block says so with `requestIgnored` rather than quietly correcting you. A batch holding a `type` or a `scroll` is unaffected, because those genuinely can end up posting and are only allowed to when you asked for the front. `type` and `scroll` also try harder before conceding it. A field that refuses an `AXValue` write now gets the text written into a selection covering its whole value, which is what a custom text view usually accepts, and an element that offers no scroll action of its own is scrolled by the scroll bar of the scroll area enclosing it. Every write is read back rather than believed, because AX reports success for a set that the app then discards, and a step reporting a background success while having done nothing is worse than one that falls back honestly. Each step result carries a `route` alongside its plane (`valueWrite`, `selectedText`, `scrollBar`, `scrollAction`, `action`, `eventStream`, `appleEvent`, `declared`), so "we found another way rather than taking your machine" is a field you can read. And the drawn pointer now sits in the target window's own stacking order instead of above everything on screen. Drive a window that's behind your editor and the pointer is behind your editor too, covered exactly as the window it's annotating is covered, because a pointer drawn on top of whatever has your attention reads as Proctor clicking in it. Note: this was measured rather than reasoned about. On macOS 26.6, ordering the overlay panel above the target window's `CGWindowID` and sampling the screen pixel where the pointer was drawn: at the old level it showed through a window fully covering the target, and at the new one it didn't, while a frontmost target still drew normally. Note: it's checked every time rather than trusted, since ordering a panel against another process's window isn't a documented capability. If the placement doesn't hold when the window list is read back, or the window can't be correlated to an id at all, the pointer goes back to floating and is drawn dimmed with a dashed pulse, which says it can't vouch for where it is. Note: a target that isn't on screen (minimised, or on another Space) gets no pointer at all, rather than one drawn over the Space you're looking at. One panel per display as before, and `PROCTOR_CURSOR=0` still turns the whole thing off.
- **Proctor tells you when the tool it recommends isn't installed.** Proctor hands browser pages to Obscura rather than driving them through the accessibility tree, and until now it did that whether or not Obscura was on the machine. Being sent to a command that doesn't exist is worse than getting no advice, because the handoff reads as an instruction from something that knows what it's talking about. When Obscura is missing, the `browser` object drops the recommendation and the command templates and carries a `toolUnavailable` saying what's missing and who installs it. The page URL stays, because that's a fact about the page rather than advice, and it's what makes the recommendation actionable the moment the install finishes. A page Obscura couldn't open anyway, a `chrome://` or the built-in PDF viewer, gains nothing new; there was no recommendation to repair. `proctor_doctor` reports `obscuraAvailable`, the path it was found at, and every path it looked in, and none of it touches `ready`, because Proctor drives native apps without Obscura and a health report that failed on an advisory tool would be lying about what's broken. The status window gains an Obscura row, the exact install command for this Mac's architecture, and buttons to copy it, open the project page, and re-check. **Proctor never installs anything**, and no tool result ever carries a shell command. That's a decision rather than an oversight: a command in a tool result is a thing a model runs, and the install is a download of an unsigned binary from the internet by a process already holding Accessibility and Screen Recording. The window's answer to a missing permission has always been Open Settings rather than granting it for you, and a missing tool gets the same shape of answer. Note: detection reads the filesystem and never runs the binary. A launchd agent inherits no login shell's `PATH`, so `~/.local/bin`, `~/.cargo/bin` and `/opt/homebrew/bin` have to be checked by name, and those are directories anything can write to; reading a mode bit runs nothing. The cost is that Proctor learns no version, and that a file planted under that name would be reported as present. Note: Obscura ships two executables that have to sit in the same directory, so a half install is reported as available with the missing sibling named rather than as clean. Note: the answer is cached for five minutes when it's there and fifteen seconds when it isn't, so an install shows up without restarting the agent; `proctor_doctor` always re-checks and writes the fresh answer through, which is what the Re-check button drives. Note: Proctor searches a launchd agent's paths, not your login shell's, so it can report missing where your terminal finds it. That's why it lists every path it checked.

- **Proctor tells you when it has been updated underneath itself.** Upgrading replaces the app on disk while the menu bar app carries on running the build it started with. The installer kickstarts the background agent, so that half comes back on the new binary; nothing restarts the menu bar app, so it can sit there on an old build indefinitely with nothing anywhere saying so. That is not hypothetical: it happened on this machine, and it got reported as a bug in a feature that was working correctly. The menu and the status window now say **Proctor was updated** and give you a **Relaunch** button. Detection is by file identity, the inode and size of the app binary, the agent binary and one of the character's pictures, checked on the polling Proctor already does, so it costs no new timer. Note: a version string would not have caught this one, because the version is currently a constant and would have read the same on both builds. Note: relaunching leaves the agent alone, and any run in flight with it. The one exception is when the agent's own binary changed too; then the relaunch restarts that as well, and the window says so before you press it.
- **When Proctor has to take the front, it says so on every display, and it can hold the machine while it does.** A step that can only travel the event stream (a click, a hover, a drag, a keystroke tested as a keystroke) puts a translucent panel over every screen naming the app Proctor is driving and how to stop it. One panel per display, never one spanning them, for the reason the drawn pointer already learned the hard way. It goes up once for the batch rather than flashing between every pair of clicks, it never takes a click itself, and it sits below the run panel so Pause and Stop stay usable above it. Note: it doesn't get into your evidence, and that was measured rather than assumed. With the panels up, a window-scoped capture of the app under test moved 0.004 mean levels against a 0.002 noise floor, while a display capture moved 5.979 with the exclusion switched off; the second number is what proves the tint was genuinely on screen while the first one says it never reached a frame. Reduce Motion drops the fades, and Reduce Transparency puts a solid plate behind the label rather than making the whole screen opaque, because somebody watching Proctor drive their Mac still has to see what it's doing. `PROCTOR_TAKEOVER=0` turns it off.
- **Proctor can swallow your input for the moments it's genuinely posting events, and that ships off.** Blocking input means a `CGEventTap`, the same API a keylogger uses, on the Accessibility grant Proctor already holds and with no prompt for anyone to see. Proctor already decided the smaller version of this question when the passive input monitor shipped opt-in, so the stronger one follows it: `PROCTOR_TAKEOVER_INPUT=1` turns it on and a default install gets the statement without the hold. Switched on, it holds the keyboard and mouse only while a step is actually posting, and it passes only the events Proctor itself posted. Note: that pass rule is load-bearing rather than tidy. A swallowing tap eats this process's own posted events, measured on macOS 26.6, so a block without it would break every foreground step it was drawn for. It never swallows a modifier, and it never swallows half a gesture: an up only goes when its own down went, so starting a hold in the middle of your drag can't leave an app holding a button nobody is pressing. Cmd-Tab, Cmd-Opt-Esc, Ctrl-Cmd-Q and the screenshot chords always pass, so you can always switch app, force quit, lock the screen or photograph what's happening. Escape stops the run. Note: anything it swallows is handed to the yield, so your first keystroke is eaten before it can corrupt the step and is also what makes Proctor let go; the run pauses, the panel comes down and your second keystroke lands. Note: the hold can't outlive the step, the run or the process. A deadline on the tap's own thread releases it whatever happened to the run that armed it, and a tap dies with its process immediately, which was measured by arming one in a second process and watching delivery resume the instant that process exited. `proctor_act` and a flow replay return a `takeover` block saying whether the machine was held, for how long, and how often somebody fought it; `proctor_doctor` reports whether the block was asked for, whether it's actually available, and your Input Monitoring state, since a keyboard tap is gated on a grant Proctor doesn't otherwise need.
- **The audit trail is signed, so an entry somebody else added is detectable.** Encrypting it at rest hid what was in it, and that was all it did. Sealing needs only the public key, and that key sits in a file beside the log, so anyone who could read the trail could also append a well-formed entry that decrypted cleanly and looked exactly like a real one. Each entry now carries a fingerprint of the entry before it plus a signature over that link, made by a key held in this Mac's secure element. The key can't be copied off the machine; what's stored is a wrapped blob that means nothing anywhere else. Neither half would do on its own, which is why both are here: a chain's links are public, so anyone who can read the file can recompute a consistent one, and a signature alone catches a forged entry but not a deleted one. Together, an inserted entry has no valid signature, a deleted one breaks a link, a reordered pair breaks two, and an edited one fails both. Entries cut from the end, and a trail rolled back to an older copy of itself, are caught against a mark of how far the trail had got, which lives in the protected key store rather than in a file next to the trail; a marker on disk gets restored along with the trail from any snapshot, and the restored pair then verifies perfectly. An entry that can't be signed is dropped rather than written unsigned, because an unsigned entry couldn't be told apart from a forged one. Entries written before this change are reported as predating it, neither clean nor forged, and the first signed entry pins that older history, so an edit to it after today shows up. `proctor_policy` status and the audit tail now carry `auditVerdict`: whether the trail is clean, how many entries verified, how many predate signing, and the first fault with its position. What this doesn't claim is worth stating plainly. Anything running as this user on this Mac can ask the key to sign, exactly as Proctor does, so an agent that can sign can sign a lie it was told to write. The claim is narrower and it's the useful one: a clean verdict can't be manufactured anywhere other than here. Detection, not prevention.
- **The trail records that Proctor recommended a browser lane.** Proctor tells a model which browser tool should own a page and never drives one itself, so nothing either tool does reaches the trail. The recommendation is Proctor's own act though, and until now there was no record it happened. The trail now records which lane was named, which rule chose it, and the scheme of the address, once per browser per run rather than on every advisory that carries it. It records nothing else about the page: no address, no host, no path, no query, no fragment. A URL in an audit entry is somebody's browsing history in a file Proctor keeps, so the recorded facts are the ones the decision was actually made on and stop there. A redacted address was considered and dropped, and the reason generalises: length plus a hash is safe for a password because a password can't be guessed, and an address can, so anyone holding a list of candidate addresses could match it back.

### Changed

- **A layout assertion that says "left-aligned" now means it.** `proctor_assert`'s `horizontalAlignment` kind tells you whether an element sits left, centre or right inside its container (a container node or rectangle you name, or the window frame when you name none). It shipped with several decisions that quietly weakened it, and this replaces them. The tolerance you pass is now one distance applied to all three placements; it used to be tripled for the two edges and left alone for the centre, so an element 24pt out of line still reported `left` while the same drift on the centre reported `custom`. The default is 1.0pt, the same as every other geometry assertion on the tool, instead of 8.0; copying a tolerance from one assertion to the next used to change strictness eightfold with nothing saying so. It now accepts `left`, `leading`, `center`, `centre`, `right` and `trailing`, rather than an alias for leading and nothing at all for trailing, and it reports the physical word, because it compares screen coordinates and doesn't read layout direction. In a container barely wider than its element the nearest placement wins; centre used to win by precedence, so an element filling its row failed a `right` check it hadn't broken. Only a genuine tie comes back as unknown rather than wrong, which in practice means an element that fills its container, or two placements that describe it to within one screen pixel. Four answers that used to be given silently are now reported instead: a `container` you asked for that has no readable frame is no longer measured against the window in its place, a frame that arrives with a nonsense width is no longer classified from comparisons that quietly fail, an assertion with no `expected` no longer asserts `leading` on your behalf, and a failure names all three measured offsets, the tolerance it used, and the likely fix when the container fell back to the window.

- **"Re-check now" is gone from the menu.** The refresh it triggered already runs on a repeating 2-second timer for as long as Proctor is running, window open or closed, so the button advanced a read by about two seconds. For the one permission it was there for it advanced nothing: the agent reads Screen Recording by asking ScreenCaptureKit, macOS caches that answer for the life of the process, and re-asking the same long-lived agent gets the same denial every time. Only a restart clears it, which is why granting through Proctor's own dialog already restarts the agent. In its place the menu offers **Restart Agent**, but only when the window can see for itself the grant the agent is denying, so a Mac that hasn't granted Screen Recording never gets a button that can't help; it says so when a run is in flight, because the restart stops it. A wedged agent, which the menu had nothing to say about before, now gets **Start Agent**.
- **Screenshots now fit the vision ceiling by default.** An oversized frame gets downsampled by the vision API anyway, so the only real question was whether that shrink happens where the scale factor is measured and reported, or where it's invisible and every coordinate the model hands back is quietly offset from the real screen. `proctor_capture` normalises to roughly 1568px on the long edge and 1.15MP, and reports the exact factor as `normalization.scale`, so you map a coordinate back with `native = normalised / scale`. Pass `normalize: false` when you want native pixels for a pixel-plane assertion, or set `normalizeMaxLongEdge` and `normalizeMaxPixels` to match a provider's tile grid (768 for Gemini, where crossing a tile boundary by a few pixels can double the token cost).
- **`proctor_capture` and `proctor_zoom` take a format.** Pass `format` as `"png"` or `"jpeg"` and `quality` between 60 and 100. PNG stays the default because it's what keeps small UI text readable: on a 3456x2234 retina capture normalised to the vision ceiling, macOS Vision OCR recovered 94% of the native-resolution words from PNG, 91% at JPEG q85 and 78% at q50, and the count of words misread as a *different* real word (which a model will happily act on) rose from 11 to 20 to 66. Note: WebP would be the better lossy container here, but macOS ships no encoder for it, so treat JPEG as a way to archive a lot of frames rather than a way to read a UI.
- **A leaner tool catalogue, and the installer now suggests `--profile core`.** The catalogue is re-sent on every turn and survives context compaction, so it's a standing cost you pay before any work happens. `--profile full` advertises all nineteen tools at roughly 11.3k tokens; `--profile core` advertises the ten that actually drive a Mac (apps, snapshot, find, act, capture, zoom, wait, assert, menu, doctor) at roughly 6.8k. Widen to `--profile scripting` or `--profile full` when you need flows, policy, kill or the CUA adapters.
- **Quit means everything.** Quitting Proctor now stops the background agent as well as the window. Both come back at your next login.
- **Replaying a recording is now gated and logged like driving the app by hand.** A flow recorded when an app was allowed used to replay just fine after an operator blocked it, and not one of those steps reached the audit trail. Replay and `proctor_stability` now pass the same policy gate as `proctor_act`, judged on the app behind the window being driven right now rather than the one named in the recording, and a target with no resolvable bundle id is refused outright when an allow list is in force. Every replayed step is written individually, with typed text and script bodies reduced to length plus SHA-256 exactly as a live step is, and the trail names its driver so you can tell them apart: `proctor_act`, `proctor_flow.replay`, `proctor_stability.replay`, `proctor_stability.reset`. `proctor_stability` re-checks permission before each repeat, so a time-limited approval token genuinely expires mid-run; the run stops there, reports how many repeats it completed, and a truncated run is never reported deterministic. Note: recording, listing, showing and deleting a flow drive nothing, so they stay ungated.
- **The audit trail is encrypted at rest.** Every entry is sealed on its own to a key that lives in this Mac's login keychain, which is never synced and never backed up, so the log is unreadable if the file is copied off the machine, restored from a backup, or opened by another account. Writing doesn't need that key, only reading does, so an unattended run keeps recording between a restart and the first time anybody unlocks the Mac. An entry that can't be sealed is dropped rather than written readable, and `proctor_policy` status now reports `auditWritable` and a count of anything lost, where a failed write used to be silent. Note: a readable trail left by an earlier version is converted in place the first time the agent writes, all or nothing, and that removes the last readable copy of it; there's no recovery key and no export, so losing the keychain key means losing the history. What it doesn't claim: hiding how many entries there are or when they happened, spotting a deleted or forged entry, or keeping out a program already running as you.

### Fixed

- **Proctor opens when you open it, even while its agent is running.** The agent is a second executable inside the app bundle, started by launchd, and macOS had been recording it as a running copy of Proctor itself. So `open -a Proctor`, and double-clicking Proctor in `/Applications`, activated a process that has no window and then reported success. Nothing appeared and there was no error to read; the installer's final "opening Proctor" step was a silent no-op on every reinstall. The agent now declares an identity of its own to LaunchServices, so opening Proctor opens Proctor. Its code signature is deliberately unchanged, which is what keeps your existing Accessibility and Screen Recording grants working across the upgrade instead of asking you for them again, and the build now refuses to produce an app where either of those two properties has broken.

- **`proctor_doctor` can no longer hang on its own first question.** It reads the Screen Recording grant by asking ScreenCaptureKit for shareable content, and the code assumed that call either answers or throws. Measured on 15 August it did neither; it parked and never came back, while the same call from a plain script on the same Mac answered in 0.037 seconds. `proctor_doctor` is the first call the Proctor skill tells a model to make, so a campaign could stall on its opening move with nothing to read. The probe is now bounded at 1.5 seconds, and a grant macOS did not answer for reports a third state, `unconfirmed`, rather than borrowing the word for a denial. That distinction is the whole point: calling it denied sends somebody to System Settings to grant a permission they may already have granted. Every entry in `grants` now carries `state` (`granted`, `denied` or `unconfirmed`) beside the existing `granted` boolean, which now means confirmed granted and stays false for the other two, so nothing that reads only the boolean over-claims. `ready` is false while a required grant is unconfirmed, because ready means established-good. The remedy text names the bound and says to call `proctor_doctor` again or restart the agent, instead of pointing at System Settings; the status window drops its **Open Settings** button for an unconfirmed grant, and the menu bar shows its own symbol rather than the missing-permission triangle, which would be reporting a fault the machine has not been shown to have. A definite answer is cached for the life of the agent, which is how macOS caches it per process anyway; a non-answer never is, because it is a property of the moment rather than of the process, and remembering one would leave the agent giving that same non-answer for the rest of its life. If the abandoned probe does eventually come back, the next call picks its answer up. Note: the full test suite runs unskipped again; two suites had been skipped for two waves because six tests hung on this same call.

- **Stop stays clickable while Proctor is driving.** The run panel has to get out of the way when Proctor posts a click, or Proctor's own click lands on the panel instead of the app underneath. That used to mean the whole panel went click-through for the whole of every such step, so a person reaching for Stop clicked straight through it into the app being driven. The kill switch was dead, and the same gesture disturbed the run it was meant to end. Now the panel only steps aside when the step is about to post an event, and to post it where the panel is standing, so everywhere else Stop works right through the step. The new rule also covers a scroll or a keystroke that quietly falls back to a synthetic event, which the old one missed because it went by the step's type rather than by what the step actually did, and the panel comes back the moment the step settles rather than staying transparent until the next step starts. If you have turned on the optional input hold with `PROCTOR_TAKEOVER_INPUT`, a click on Stop now ends the run on the first press instead of the second. Proctor's own clicks still cannot press Stop, and that is enforced twice over. One case is unchanged and worth knowing: with the input hold off and a step posting into the panel's own corner, that click still reaches the app underneath.

- **A hold now stops only the run that noticed it.** One shared latch used to park every run in flight, so an accessibility-only run in another session driving a different application would stop dead for up to fifteen minutes with nothing said to anyone about why. The automatic hold belongs to the run that read the contention. A person's Pause still holds everything, because that is a decision about the machine rather than a reading about one event stream.
- **A run starting no longer lifts another run's hold.** The scheduler never consulted the halt latch, so any run beginning on a free lane cleared a live hold along with its clock and its limit, and the held run carried on posting into the person it had just got out of the way of.
- **An expired hold gives up on one run instead of all of them.** When the fifteen-minute limit runs out on an automatic hold it now ends that run alone. It used to stop every run that was going at the time and tell each caller that a person had stopped it from the run HUD, which is a halt nobody chose reported as somebody's decision.
- **The window shows the permissions you have already granted.** A name mismatch between the window and the agent meant every check read as "agent not answering", even with both grants in place. The window reads the agent correctly now, and reflects a grant within a couple of seconds of you making it. Granting Screen Recording restarts the agent for you, so it stops asking for a permission you just gave.
- **Secure Event Input no longer wears the missing-permission warning.** Proctor's menu bar shows the character when it can work and a status symbol when it can't, and the symbol for "a permission is missing" was also being shown whenever Secure Event Input was active. That happens every time a password field takes focus, and for as long as Terminal has Secure Keyboard Entry switched on, so a Mac with every grant in place was wearing a permission warning several times a day. It has its own symbol now, a locked laptop, rather than the warning triangle. It still takes the character off the menu bar, because clicks and keystrokes really are dead while it's on and that's worth knowing before you start a run rather than four steps into one. A missing permission outranks it when both are true. Note: `proctor_doctor` is unchanged. It still reports `secureEventInputActive` and still lists it as a blocker, because a model asking whether every plane will work needs that answer, and the menu bar is asking a narrower question.
- **A menu bar picture that won't load no longer reports success.** When the character's art couldn't be decoded, the menu bar fell back to a checkmark seal, which reads as everything being fine. That same seal was also what Proctor showed for ready before the character existed, so one picture meant three different things at once and a stale menu bar looked exactly like a broken readiness rule. The fallback is a question mark circle now, which appears nowhere else.

## [0.1.0] - 2026-08-14

First public release.

### Added

- **Computer use over MCP.** Any MCP-speaking model can drive this Mac: read the screen, find controls, click, type, scroll, and check that what it did actually landed. Nineteen tools in all, from `attach` and `snapshot` through `find`, `act`, `capture`, `zoom`, `wait` and `assert` to `flow`, `stability`, `inspect` and `doctor`.
- **A real UI-testing harness, not just a driver.** `assert`, `wait`, `stability` and `flow` turn the same tools into acceptance checks: wait for a window to settle, assert an element is there, replay a sequence, and get told when the screen is still moving.
- **Windows in the background stay in the background.** Proctor drives occluded windows, minimised windows, and windows on another Space without pulling focus or stealing your pointer, working across the accessibility and Apple Events planes rather than faking clicks at the front.
- **Screenshots that tell you how old they are.** Captures come back through ScreenCaptureKit with freshness metadata, so a model acting on a frame knows whether it is looking at now or at a moment ago.
- **Grants that survive an upgrade.** Accessibility and Screen Recording are granted once to a stable launchd-agent identity keyed to the Developer ID signature, not to a path or a build, so a reinstall or a version bump does not send you back to System Settings.
- **The tools every model already knows.** Stock Anthropic and OpenAI computer-use schema façades sit over the native tools, so a model trained on either can attach with no custom wiring.
- **Menus, dictionary, a policy gate, and a redacting audit log.** Read menu bars, look words up, gate actions behind a policy, and keep an audit trail that redacts what it should not record. Plus process kill and screen unlock for the moments automation gets stuck.
- **Signed, notarised, and installed properly.** The first public build ships as a notarised Developer ID release into `/Applications`, run as a per-user launchd agent.
