# Changelog

All notable changes to Proctor are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **A menu-bar icon that is always there, and starts with your Mac.** Proctor registers itself to launch at login and lives in the menu bar, so it is one click away without hunting for the app. The menu shows what it is doing right now: the tool it is running, the last one it ran, or that it is idle.
- **Onboarding that asks for both permissions on one screen.** First run is now a single sheet in the register of a system permission prompt: the two grants side by side, each with an Allow button that triggers the real macOS dialog, and the steps animate rather than jump. Motion respects Reduce Motion.
- **Proctor draws a pointer while it drives an app.** An accessibility press actuates a button with nothing moving on screen, which is exactly what lets a run work on a background window and exactly what makes it impossible to follow; somebody watching sees menus open and text appear with no cause. The pointer travels to each step's target before the step fires, leans into the direction it's travelling, and pulses where it acts. It draws one panel per display rather than one spanning them all, and that isn't a stylistic choice: a panel sized to the union of a 1728x1117 laptop and a 2560x1440 display is a 26-megapixel backing store that the window server accepts and reports as onscreen with alpha 1, and then never presents. Note: it never appears in a `proctor_capture`, because captures are window-scoped to the app under test, so it can't move a state hash or change a pixel assertion. Set `PROCTOR_CURSOR=0` to turn it off for an unattended suite, or for a machine somebody else is working on.
- **A panel that tells you what Proctor is doing, and a button that stops it.** A run used to be invisible unless you were watching the drawn pointer, and there was no way to halt one short of quitting the agent. A run now puts a small panel over the app it is driving: one line naming the step in flight, a step counter, a progress rail along the panel's own bottom edge, the last three steps with how long each took to settle, a run clock, and Pause and Stop. Pause holds before the next step and lets the one in flight finish settling, because killing a step halfway through leaves the app in a state nobody can describe; Stop ends the run there. A stopped run still reports the steps it completed, and attaches the refusal to the first step that never ran under its own code, `haltedByPerson`, so the model that asked can tell a person's decision from a policy rule or a broken app. Every kind of run shows it: a batch, a replayed flow, a stability sweep, and both computer-use façades. The panel is neutral graphite over whatever it floats above, with one colour carrying the state, and it follows your light or dark setting. Note: it needs the agent to run an application event loop, which it now does, and that is the one behavioural change worth knowing about; settling is unaffected, because the accessibility observers it depends on were already registered on the common run loop modes. A pause nobody resumes gives up after fifteen minutes and reports itself the way a stop does (`PROCTOR_HUD_PAUSE_LIMIT`, in seconds, to change that). Only the grip and the two buttons are live, so nothing else on the panel reacts to a click; a click on the body is discarded rather than handed to the app underneath, and the panel gets out of the way entirely while Proctor is posting a synthetic click, hover or drag, so a step aimed at a point under the panel still lands on the app. The panel is excluded from screen sharing and never appears in a `proctor_capture`, so watching a run cannot change its evidence. Set `PROCTOR_HUD=0` to turn it off for an unattended machine or one somebody else is using; it is separate from `PROCTOR_CURSOR`, so you can keep either without the other. `proctor_doctor` gains a `hud` block saying whether the panel is actually on screen, because believing you have a stop button you do not have is worse than knowing you have none. The character's bay is drawn and left empty, and the queue bar is not built yet; both arrive with their own changes.
- **The determinism run can now show you the step, not just score it.** `proctor_stability` replays a flow N times and tells you where the runs stopped agreeing, which is the right answer to "is this flaky" and a useless one when you want to see what step 7 actually looked like on the replay that diverged. Pass `captureEach` and every step that runs, in every replay, writes a PNG through the same step-running path that `act` and `flow` replay use, so the frames are genuinely per-step rather than N pictures of the end state. A replay that breaks mid-flow photographs the steps before the break and reports the rest as not attempted, rather than claiming a frame it never took. Pass `pointerMarks` as well and each frame gets a marker composited where that step acted. The report gains a `captures` ledger whose every entry names its replay index, its step index and its file locations, because a flat per-step list can't say which replay a frame came from and comparing one step across replays is the whole point. Both switches are off by default and the scoring is untouched: `firstDivergence`, `stepInstability`, `deterministic` and `divergenceDetail` are computed exactly as before. Note: capturing after every step moves the run's timings, so the report says so rather than letting a captured run's score be compared quietly against one taken without. Asking for `pointerMarks` with `captureEach` off turns capture on and tells you, rather than accepting a switch that does nothing. An opt-in run writes roughly runs × steps images, doubled where a marker is drawn, and nothing cleans them up. The marker annotates where the step acted and is not a live cursor; Proctor drives through the accessibility and Apple Events planes and doesn't move the system pointer. A step whose frame or marker couldn't be produced says so in the ledger, and doesn't fail the run or change its score.
- **Two sessions can now share a Mac without standing on each other.** Proctor is one agent behind one socket and any number of MCP clients can connect to it, and until now nothing arbitrated between them: two sessions driving the same machine interleaved their steps, and the second one's synthetic click landed in whatever window the first had just raised. The recorded step order in a test with the scheduler taken out is one, two, one, two, one, two, two, one, which is the failure exactly. There is now a scheduler, and it is three lanes rather than one queue, because queueing everything would make Proctor feel broken for the common case. Reads never join the line: `snapshot`, `find`, `capture`, `menu`, `zoom` and `assert` observe without mutating and run immediately, always. An accessibility press is IPC to one process, so two sessions driving different applications genuinely run in parallel; two on the same application take turns. A synthetic `click`, `hover`, `dragPath` or `key`, a batch that asked for `foreground`, and a `raise` step all take the whole machine, one at a time anywhere on it, because each of them changes what is in front and therefore where everybody else's clicks land. What queues is a whole batch, never a step: a six-step login is not split across two sessions' turns, and a stability sweep holds its lanes across every repeat rather than rejoining the line between them. Each session is named for the process on the other end of the socket, never for anything the client sends: its working directory gives the project and a four-character id separates two sessions in the same repo, so the panel prints `proctor-mcp a3f1`. A connection that could name itself could name itself as somebody else's project in the very UI a person uses to decide whose run to stop. A call that has to wait is held open until its turn instead of being answered with a position it would have to re-send, and gives up after forty-five seconds saying the machine was busy and where it stood (`PROCTOR_QUEUE_WAIT_LIMIT`, in seconds, to change that); a caller told nothing retries, and a retry behind a queue is how a queue becomes a stampede. One session may keep three runs waiting and a fourth is refused on the spot, so a session in a loop cannot starve the others. It is first come, first served within a lane, and a run that needs the whole machine becomes a barrier once it reaches the head of the line rather than being walked past forever. The run HUD gains an `N sessions waiting` bar between the step trail and the run controls, absent entirely when nothing is waiting, expanding in place to each run's position, session, what it wants and how long it has waited, with a drop control per row and Hold and Clear in the list header. Hold stops any waiting run starting, the active session's own next one included, and leaves the run in flight alone; Clear removes every waiting run and leaves the active one untouched. The queue's controls are Hold and Clear and the run's are Pause and Stop, never adjacent and never sharing a word, because two controls both called "pause" is how somebody stops the wrong thing. The menu bar mirrors the waiting count, so the queue is answerable without the panel on screen, and `proctor_doctor` gains a `queue` block reporting how many runs are active and waiting per lane, whether the queue is held, and how long each active hold has been held. Note: when a person clears the queue or drops a run, that caller's call comes back under `haltedByPerson` saying a person removed it rather than that a step failed, since one is a signal to stop and ask and the other a signal to retry; a refusal that is nobody's decision uses a new code, `queueBusy`, which always means nothing was actuated and the call is safe to send again. The permission gate is read a second time once a run's turn comes, so a time-limited approval that expired while the run waited refuses it rather than letting it drive on stale authority. A long sweep may hold its lanes for its whole length and only a person's Stop shortens it; the forty-five second ceiling caps how long anybody waits, never how long a run may take. And a waiting caller that has gone away cannot be seen to have gone from where the wait happens, so it keeps its place until its turn comes or the ceiling fires.
- **The run panel has a character in it now.** The bay at the left of the panel shipped empty; it now holds a small compact Mac whose screen changes with the run. Dot eyes while it waits, leaning with speed lines while it travels to a step's target, an orange screen while it presses something, a warning while blocked, grey pause bars while paused, a tick when the run finishes and a cross when it fails. The screen is what carries the state rather than a face or a pose, which is what keeps all seven readable at 38 points, and paused is the only grey one so it reads without relying on colour. Idle, travelling and acting move; the other four hold still. The loop is handed to the render server in one pass, so the agent never draws a frame of it while it is busy watching an app settle, which is the same reason the drawn pointer works that way. Note: Reduce Motion stops the character and the progress rail's pulse, and every state still reads from its screen alone, because that was the rule the character was drawn to in the first place. The art ships inside the app at standard, double and triple density, so nothing is fetched while a run is going, and a picture that will not load leaves the bay empty rather than stopping the run.

### Changed

- **Screenshots now fit the vision ceiling by default.** An oversized frame gets downsampled by the vision API anyway, so the only real question was whether that shrink happens where the scale factor is measured and reported, or where it's invisible and every coordinate the model hands back is quietly offset from the real screen. `proctor_capture` normalises to roughly 1568px on the long edge and 1.15MP, and reports the exact factor as `normalization.scale`, so you map a coordinate back with `native = normalised / scale`. Pass `normalize: false` when you want native pixels for a pixel-plane assertion, or set `normalizeMaxLongEdge` and `normalizeMaxPixels` to match a provider's tile grid (768 for Gemini, where crossing a tile boundary by a few pixels can double the token cost).
- **`proctor_capture` and `proctor_zoom` take a format.** Pass `format` as `"png"` or `"jpeg"` and `quality` between 60 and 100. PNG stays the default because it's what keeps small UI text readable: on a 3456x2234 retina capture normalised to the vision ceiling, macOS Vision OCR recovered 94% of the native-resolution words from PNG, 91% at JPEG q85 and 78% at q50, and the count of words misread as a *different* real word (which a model will happily act on) rose from 11 to 20 to 66. Note: WebP would be the better lossy container here, but macOS ships no encoder for it, so treat JPEG as a way to archive a lot of frames rather than a way to read a UI.
- **A leaner tool catalogue, and the installer now suggests `--profile core`.** The catalogue is re-sent on every turn and survives context compaction, so it's a standing cost you pay before any work happens. `--profile full` advertises all nineteen tools at roughly 11.3k tokens; `--profile core` advertises the ten that actually drive a Mac (apps, snapshot, find, act, capture, zoom, wait, assert, menu, doctor) at roughly 6.8k. Widen to `--profile scripting` or `--profile full` when you need flows, policy, kill or the CUA adapters.
- **Quit means everything.** Quitting Proctor now stops the background agent as well as the window. Both come back at your next login.
- **Replaying a recording is now gated and logged like driving the app by hand.** A flow recorded when an app was allowed used to replay just fine after an operator blocked it, and not one of those steps reached the audit trail. Replay and `proctor_stability` now pass the same policy gate as `proctor_act`, judged on the app behind the window being driven right now rather than the one named in the recording, and a target with no resolvable bundle id is refused outright when an allow list is in force. Every replayed step is written individually, with typed text and script bodies reduced to length plus SHA-256 exactly as a live step is, and the trail names its driver so you can tell them apart: `proctor_act`, `proctor_flow.replay`, `proctor_stability.replay`, `proctor_stability.reset`. `proctor_stability` re-checks permission before each repeat, so a time-limited approval token genuinely expires mid-run; the run stops there, reports how many repeats it completed, and a truncated run is never reported deterministic. Note: recording, listing, showing and deleting a flow drive nothing, so they stay ungated.
- **The audit trail is encrypted at rest.** Every entry is sealed on its own to a key that lives in this Mac's login keychain, which is never synced and never backed up, so the log is unreadable if the file is copied off the machine, restored from a backup, or opened by another account. Writing doesn't need that key, only reading does, so an unattended run keeps recording between a restart and the first time anybody unlocks the Mac. An entry that can't be sealed is dropped rather than written readable, and `proctor_policy` status now reports `auditWritable` and a count of anything lost, where a failed write used to be silent. Note: a readable trail left by an earlier version is converted in place the first time the agent writes, all or nothing, and that removes the last readable copy of it; there's no recovery key and no export, so losing the keychain key means losing the history. What it doesn't claim: hiding how many entries there are or when they happened, spotting a deleted or forged entry, or keeping out a program already running as you.

### Fixed

- **The window shows the permissions you have already granted.** A name mismatch between the window and the agent meant every check read as "agent not answering", even with both grants in place. The window reads the agent correctly now, and reflects a grant within a couple of seconds of you making it. Granting Screen Recording restarts the agent for you, so it stops asking for a permission you just gave.

## [0.1.0] - 2026-08-14

First public release.

### Added

- **Computer use over MCP.** Any MCP-speaking model can drive this Mac: read the screen, find controls, click, type, scroll, and check that what it did actually landed. Nineteen tools in all, from `attach` and `snapshot` through `find`, `act`, `capture`, `zoom`, `wait` and `assert` to `flow`, `stability`, `inspect` and `doctor`.
- **A real UI-testing harness, not just a driver.** `assert`, `wait`, `stability` and `flow` turn the same tools into acceptance checks: wait for a window to settle, assert an element is there, replay a sequence, and get told when the screen is still moving.
- **Windows in the background stay in the background.** Proctor drives occluded windows, minimised windows, and windows on another Space without pulling focus or stealing your pointer, working across the accessibility and Apple Events planes rather than faking clicks at the front.
- **Screenshots that tell you how old they are.** Captures come back through ScreenCaptureKit with freshness metadata, so a model acting on a frame knows whether it is looking at now or at a moment ago.
- **Grants that survive an upgrade.** Accessibility and Screen Recording are granted once to a stable launchd-agent identity keyed to the Developer ID signature, not to a path or a build, so a reinstall or a version bump does not send you back to System Settings.
- **The tools every model already knows.** Stock Anthropic and OpenAI computer-use schema façades sit over the native tools, so a model trained on either can attach with no custom wiring.
- **Menus, dictionary, a policy gate, and a redacting audit log.** Read menu bars, look words up, gate actions behind a policy, and keep an audit trail that redacts what it should not record. Plus process kill and screen unlock for the moments automation gets stuck.
- **Signed, notarised, and installed properly.** The first public build ships as a notarised Developer ID release into `/Applications`, run as a per-user launchd agent.
