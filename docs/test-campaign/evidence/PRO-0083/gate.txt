WHERE IT BLOCKED. `sample` on the running process, on two separate full runs, put fifteen of the
sixteen cooperative threads in one stack:

  SecStaticCodeCheckValidityWithErrors  (in Security)
    Security::CodeSigning::SecStaticCode::staticValidate(unsigned int, ...)
      Security::Dispatch::Group::wait()
        _dispatch_group_wait_slow
          _dlock_wait
            __ulock_wait

in ScreenRecordingProbeWiringTests, ObscuraPresenceWiringTests, ToolchainDoctorTests and
GuestProviderTests — none of them this item's. `staticValidate` farms its page hashing to the
libdispatch global pool and waits on a group, so each blocked cooperative thread is waiting on a
worker pool that a second load can starve. This item's second load was its child processes, and
the most expensive of them was the forging arm's imposter: a hard link at a FRESH PATH is a first
launch for syspolicyd however the inode is shared. DEF-043, DEF-044.

THE FIX, in this item's test and not in the product. The forging arm no longer launches anything.
It is a raw AF_UNIX peer that is the test process itself, which `proc_pidpath` reports as
`proctor-mcpPackageTests` and `SessionIdentity.frontEnd(named:)` maps to nil — the same third-peer
condition, at no launch cost. The run went 143s → 16.4s and four issues → one.

  after the fix, load 250:  FAIL, 16.387s, 1 issue  (ScreenRecordingProbeWiringTests, 5.692 < 5.0)
  after the fix, load 176:  PASS, 21.376s, exit 0
  after the fix, load 241:  PASS, 20.261s, exit 0
  after the fix, one run wedged and was killed — see DEF-044, and note that the sample taken
  during it found ZERO threads belonging to this item: fifteen in staticValidate, all of them
  ScreenRecordingProbeWiringTests, ObscuraPresenceWiringTests and ToolchainDoctorTests.

THE ONE REMAINING ISSUE IS NOT THIS ITEM'S, and was measured rather than argued. At load ~200 with
