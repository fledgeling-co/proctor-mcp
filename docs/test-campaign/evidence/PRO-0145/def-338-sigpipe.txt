PRO-0145 / DEF-338 — a write to a closed peer killed the process by signal
date: Tue 25 Aug 2026 14:15:45 AEST

== THE PROBE, before the fix ==
A listener that accepts and immediately closes; the client writes twice.
  /tmp/sigpipe_probe  ->  exit 141   (128 + 13 = SIGPIPE)
No error was returned, nothing was written anywhere, and the process was gone.

== WHY IT MATTERS ==
proctor-shim writes every tool call down this socket. An agent dying mid-write
takes the MCP server with it: the host sees its server vanish, the caller never
receives agentUnavailable, and no audit record is written because the process is
already dead. The accepted side has the same fault in reverse — a shim hanging up
during a long batch would have taken the agent down.

== THE FIX ==
proctorSuppressSIGPIPE() sets SO_NOSIGPIPE per socket, turning it into EPIPE on
the call, which every send path here already handles as 'the connection closed
while sending'. Set per socket rather than by installing a process-wide SIG_IGN:
a library has no business changing a signal disposition its host may depend on,
and the Reflector is embedded in somebody else's application.

Four sites, plus the accepted descriptor, which does NOT inherit the option:
  Sources/ProctorCore/Transport.swift:18:/// `SO_NOSIGPIPE` turns it into `EPIPE` on the call, which every send path here
  Sources/ProctorCore/Transport.swift:129:        if s >= 0 { proctorSuppressSIGPIPE(s) }
  Sources/ProctorReflector/SocketServer.swift:47:            setsockopt(fd, SOL_SOCKET, SO_NOSIGPIPE, &on, socklen_t(MemoryLayout<Int32>.size))
  Sources/ProctorAgent/Server.swift:42:        // disposition is to terminate. See proctorSuppressSIGPIPE.
  Sources/ProctorAgent/Server.swift:43:        if fd >= 0 { proctorSuppressSIGPIPE(fd) }
  Sources/ProctorAgent/Server.swift:108:            // An ACCEPTED descriptor does not inherit SO_NOSIGPIPE from its
  Sources/ProctorAgent/Server.swift:112:            if client >= 0 { proctorSuppressSIGPIPE(client) }
  Sources/ProctorAgent/Server.swift:120:            setsockopt(client, SOL_SOCKET, SO_NOSIGPIPE, &on, socklen_t(MemoryLayout<Int32>.size))

== AFTER ==
Test "a listener that hangs up on accept is an error, not a signal" passes.

CORRECTED 2026-08-25 by the tailings pass. That sentence previously continued
"Before the fix the whole test process died at that line", and it is wrong.
Measured by removing proctorSuppressSIGPIPE from Transport.swift and re-running:

  swift test --filter SocketBoundaryChaosTests/hangUpOnAccept   -> returncode 0
  swift test --filter SocketBoundaryChaos (whole suite)         -> returncode 1

So the suite DOES arm the fix and that test does NOT. One send into a peer that
has closed gets EPIPE returned; SIGPIPE needs a second write after the FIN has
landed, which is why the two-write probe measured 141 and a single send does not.
The discriminating case is the repeated-failure one, which writes fifty times.

Naming a test that does not bite is the same fault this wave described elsewhere
as an assertion nobody wrote wearing the name of one. The defect, the fix and the
suite-level arming are unaffected; only the attribution was wrong.
