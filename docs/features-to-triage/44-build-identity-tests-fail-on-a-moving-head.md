# The build-identity tests fail whenever HEAD moves without a source change

## The measurement

PRO-0030 shipped `BuildInfo`, generated by a SwiftPM build-tool plugin, and two tests that
check the generated identity against the live checkout:

```
BuildInfoTests.swift:96  (BuildInfo.current.commit → "449d5b6c652c") == (head → "f2221f60d3e9")
BuildInfoTests.swift:109 (BuildInfo.current.dirty  → false)          == (!porcelain.isEmpty → true)
```

Both failures were produced on 2026-08-15 while merging PRO-0037, in the ordinary course of
a rebase, and neither is a defect in the feature under test:

- **The dirty check fails on any worktree with uncommitted changes.** Editing one line to
  adapt a call site during a rebase makes the tree dirty while the compiled flag still says
  clean, so the gate goes red for a reason that has nothing to do with the change.
- **The commit check fails after any `git commit --amend` or rebase that moves HEAD without
  touching a source file.** The plugin's output is cached against its inputs, and git's HEAD
  is not one of them, so the generated constant keeps the old commit. `swift build` reports
  "Build complete" and re-runs nothing. Clearing `.build/plugins` forces regeneration and
  the tests go green with no source change at all.

## Why it matters beyond an annoyance

Every fleet runner gates with `swift test`, and a runner sees a red gate that its own change
did not cause. That is the most expensive kind of false signal: the runner cannot tell it
from a real break, and the correct response (delete a build cache) is not discoverable from
the failure message, which reads as a genuine mismatch between two commits.

It also weakens what the feature was for. The point of PRO-0030 was that a build says which
build it is. A cached plugin output means a freshly built binary can carry a stale commit
string, which is exactly the confusion the feature exists to remove, appearing in the one
place it was measured.

## The decision this turns on

**Whether the check belongs in the test suite at all, and if so what it may assume.** Three
readings, and they lead to different work:

- The tests are asserting a property of the *release* process, not of any developer build.
  Then they belong behind a flag the release workflow sets, and a developer build asserts
  something weaker: that the fields are well formed and non-empty.
- The tests are right and the plugin is wrong to cache across a HEAD move. Then the plugin
  needs `.git/HEAD` and `.git/index` as declared inputs, which makes every commit invalidate
  it. Say what that costs in rebuild time, because it is paid on every build.
- The dirty flag genuinely cannot be checked from inside a test that the checkout's own
  cleanliness affects. Then say so and drop that assertion rather than leaving a test whose
  pass depends on whether somebody happens to have a file open.

## Worth knowing

- The gate in use while PRO-0041 is open is
  `swift test --skip ObscuraPresenceWiringTests --skip BrowserLaneWiringTests`.
- `rm -rf .build/plugins` before the gate is the current workaround. It is a workaround, not
  the fix: a runner has to know to do it, and knowing is the thing that is missing.
- The plugin is `BuildIdentity`; its cached outputs sit under
  `.build/plugins/` and `.build/index-build/plugins/`.
