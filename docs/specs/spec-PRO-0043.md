# PRO-0043: The build-identity tests fail whenever HEAD moves without a source change

**ID:** PRO-0043
**Status:** In Review
**Created:** 2026-08-15
**Last updated:** 2026-08-15
**Plan:** `docs/plans/plan-PRO-0043.md`
**Brief:** `docs/features-to-triage/44-build-identity-tests-fail-on-a-moving-head.md`
**Tests the feature from:** PRO-0030 (`BuildInfo`, the `BuildIdentity` plugin, `scripts/gen-build-identity.sh`)

## Feature description

> ## The measurement
>
> PRO-0030 shipped `BuildInfo`, generated by a SwiftPM build-tool plugin, and two tests that
> check the generated identity against the live checkout:
>
> ```
> BuildInfoTests.swift:96  (BuildInfo.current.commit → "449d5b6c652c") == (head → "f2221f60d3e9")
> BuildInfoTests.swift:109 (BuildInfo.current.dirty  → false)          == (!porcelain.isEmpty → true)
> ```
>
> Both failures were produced on 2026-08-15 while merging PRO-0037, in the ordinary course of
> a rebase, and neither is a defect in the feature under test:
>
> - **The dirty check fails on any worktree with uncommitted changes.** Editing one line to
>   adapt a call site during a rebase makes the tree dirty while the compiled flag still says
>   clean, so the gate goes red for a reason that has nothing to do with the change.
> - **The commit check fails after any `git commit --amend` or rebase that moves HEAD without
>   touching a source file.** The plugin's output is cached against its inputs, and git's HEAD
>   is not one of them, so the generated constant keeps the old commit. `swift build` reports
>   "Build complete" and re-runs nothing. Clearing `.build/plugins` forces regeneration and
>   the tests go green with no source change at all.
>
> ## Why it matters beyond an annoyance
>
> Every fleet runner gates with `swift test`, and a runner sees a red gate that its own change
> did not cause. That is the most expensive kind of false signal: the runner cannot tell it
> from a real break, and the correct response (delete a build cache) is not discoverable from
> the failure message, which reads as a genuine mismatch between two commits.
>
> It also weakens what the feature was for. The point of PRO-0030 was that a build says which
> build it is. A cached plugin output means a freshly built binary can carry a stale commit
> string, which is exactly the confusion the feature exists to remove, appearing in the one
> place it was measured.
>
> ## The decision this turns on
>
> **Whether the check belongs in the test suite at all, and if so what it may assume.** Three
> readings, and they lead to different work:
>
> - The tests are asserting a property of the *release* process, not of any developer build.
>   Then they belong behind a flag the release workflow sets, and a developer build asserts
>   something weaker: that the fields are well formed and non-empty.
> - The tests are right and the plugin is wrong to cache across a HEAD move. Then the plugin
>   needs `.git/HEAD` and `.git/index` as declared inputs, which makes every commit invalidate
>   it. Say what that costs in rebuild time, because it is paid on every build.
> - The dirty flag genuinely cannot be checked from inside a test that the checkout's own
>   cleanliness affects. Then say so and drop that assertion rather than leaving a test whose
>   pass depends on whether somebody happens to have a file open.
>
> ## Worth knowing
>
> - The gate in use while PRO-0041 is open is
>   `swift test --skip ObscuraPresenceWiringTests --skip BrowserLaneWiringTests`.
> - `rm -rf .build/plugins` before the gate is the current workaround. It is a workaround, not
>   the fix: a runner has to know to do it, and knowing is the thing that is missing.
> - The plugin is `BuildIdentity`; its cached outputs sit under
>   `.build/plugins/` and `.build/index-build/plugins/`.

## What was measured before deciding

The brief's account of the mechanism was checked rather than taken on trust, in
`.worktrees/PRO-0043` on this toolchain, and it is right about the symptom and wrong about
the cause in a way that changes the answer.

**The failure reproduces exactly and deterministically.** With a warm `swift test` build
plan, one `git commit --allow-empty` and a re-run gives:

```
Expectation failed: (BuildInfo.current.commit → "a16cdc5bc0b6") == (head → "d411a25c8afd")
```

**The cause is not an input-tracking miss; it is that the command does not run at all.** The
plugin emits a *prebuild* command, and its own doc comment says prebuild commands "run every
time with no up-to-date check". That is false as observed here. When llbuild considers the
plan up to date, `swift build` prints `Build complete! (0.11s)` and the generator never
executes. Measured: an untracked file was created and `swift build` run three times; the
generated constant read `dirty = false` on all three. So there is no set of declared inputs
to add — the second reading in the brief has nothing to attach to, because a prebuild command
declares no inputs and the step being skipped is the whole plan.

**`swift build` and `swift test` keep separate build plans**, so whichever was last brought
up to date decides freshness. That is why the failure reads as intermittent: a `swift test`
straight after a HEAD move regenerates if the *test* plan had work to do, and does not if it
did not.

**No workflow in `.github/workflows/` runs `swift test` at all.** That disposes of the
brief's first reading: a strong assertion gated behind a release-only flag would never
execute anywhere, in a repo whose only test runner is a person or a fleet runner at a
terminal.

## The decision: test the generator, not the cache

The two failing assertions are the same mistake made twice. Both compare a value **compiled
in at some past build** against **the checkout as it is right now**. The gap between those
two is a property of SwiftPM's scheduler, not of PRO-0030, and it is not merely unproven —
it is false by construction, because nothing in the toolchain promises that the last build
happened at this HEAD.

So the check moves to where both sides are owned by the test.

### 1. The generator is tested against a repository the test builds itself

`BuildInfoTests` already has a hermetic lane: a helper that runs
`scripts/gen-build-identity.sh` against a temporary directory and reads the file it writes.
It is immune to the plugin cache because it invokes the generator directly. Today it covers
only the degraded paths — no git at all, and a repository git cannot answer for — and never
the ordinary one.

Two tests are added there, and between them they prove exactly what the deleted assertions
were reaching for:

- A temporary repository is initialised, given one commit, and the generator is run against
  it. The commit it writes is that repository's `HEAD`. This is the real content of "the
  build identity is generated from this checkout" and it is now checkable, because the test
  made the checkout.
- The same repository is then made dirty and the generator run again. `dirty` flips to
  `true` and the commit does not move. Nothing tests this today at the generator level, so
  this is new coverage rather than a like-for-like replacement.

Three things make that hermetic rather than merely temporary, and each was a hole the
out-of-family review found in the first draft of this decision.

**The generator's output goes outside the repository it is measuring.** The existing helper
writes the generated file into a directory under the package root it is given. Point that at
the temporary repository and the first run leaves an untracked file behind, so the run
intended to observe a clean tree observes the test's own output and reports `dirty = true`.
The output directory is a sibling of the repository, not a child of it.

**The git environment is sealed, for the generator as well as for the test's own calls.**
`GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE` override `-C`, so a test process that
inherited any of them would have both the test and the script reading a different repository
than the one on the path. They are cleared, and `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM`
are pointed at `/dev/null`, which neutralises inherited hooks, signing and template
configuration in one move rather than by enumerating keys. The script inherits the test
process's environment, so this has to cover the generator invocation or it covers nothing.

**The repository is given a local identity.** A commit needs `user.email` and `user.name`,
and the machine's global config is not the test's to assume — particularly once the global
config is sealed off above. None of this touches the repository under test.

### 2. The compiled identity keeps the assertion that is still true

`compiledCommitMatchesGit` loses one clause and keeps the rest. Dropped: equality with the
live `HEAD`. Kept and strengthened: **when the test's own `git rev-parse` succeeds against
the package directory**, the compiled commit is a **real commit** — twelve or more lowercase
hex characters, and neither `unknown` nor `unavailable`.

That survives a stale cache for the reason the equality does not. A stale commit is still a
commit, so the assertion holds whether the generator last ran at this HEAD or three commits
ago; the only way to fail it is for the generator to have genuinely degraded to a sentinel or
to garbage in a checkout where git was available. That degradation is precisely the silence
the suite's own header says it exists to catch, and it is the half of the original assertion
that was ever doing work.

Three details, each of which the out-of-family review showed the obvious version gets wrong.

**Twelve or more, not exactly twelve.** `git rev-parse --short=12` treats twelve as a
*minimum* and lengthens the abbreviation when twelve would be ambiguous. An exact-width check
passes today and reddens years later in a bigger repository, for no defect — the same class
of latent false alarm this spec exists to remove.

**The live git call is a precondition, not an expected value.** `unavailable` is reachable in
a real checkout with a healthy generator: dubious-ownership refusals, an unreadable `.git`, a
sandbox denial. Demanding a real sha unconditionally would red the gate for the environment
rather than for the code. So the strong clause is claimed only where the test can itself get
a sha from that directory, and skipped where it cannot. The live value is still never
compared against the compiled one.

**The failure message names the cache.** The brief's real complaint is that the correct
response was not discoverable from the failure text. Where these assertions can still fire on
a stale generated file — a tarball built before its directory became a checkout is the honest
residual — the message says to clear `.build/plugins`, so a reader who hits it is not left
diagnosing a disagreement between two commits that is not one.

### 3. The compiled dirty flag has no live invariant, so the live comparison goes

`compiledDirtyMatchesGit` loses its comparison against the working tree. The brief's third
reading is correct about that half: the compiled flag records whether the tree was dirty *the
last time the generator ran*, and the test can observe only whether it is dirty *now*. Those
are equal by coincidence. A test whose pass depends on whether somebody has a file open is
worse than no test, because it spends a runner's attention on a signal that carries none.

One invariant does survive on the compiled value, and the out-of-family review was right that
throwing it away with the rest gives up more than necessary: **a sentinel commit implies
`dirty == false`**. The generator can only reach `DIRTY=true` after resolving a real commit,
so `unknown` or `unavailable` paired with a dirty flag is an impossible state and means the
generated file was assembled by something other than this script. It costs one line, depends
on nothing outside the compiled struct, and cannot flake.

The rest of the coverage moves to the generator test in decision 1, where the test controls
when the tree becomes dirty, and to the existing `dirtyIsDistinct` test, which already pins
that a dirty descriptor differs from a clean one.

### 4. The plugin's doc comment is corrected, and nothing else about the plugin changes

The comment in `Plugins/BuildIdentity/plugin.swift` states the opposite of the measured
behaviour, and it is the sentence that would send the next reader to look for a missing
declared input that cannot exist. It is corrected to say what was observed. This is a comment
change with no behaviour attached, included deliberately because the subject of this spec is
what is actually true here, and leaving the false claim in place guarantees the measurement
is re-derived.

Fixing the staleness itself is **not** in this id's scope — see Child work found.

## Acceptance criteria

- **A1** Where the test's own `git rev-parse` answers for the package directory, the compiled
  commit is twelve or more lowercase hex characters and is neither `unknown` nor
  `unavailable`, and this holds after `HEAD` moves with no source change. Where git does not
  answer, the assertion is skipped rather than failed.
- **A2** No test in the suite compares the compiled identity against the live checkout's
  `HEAD` or working-tree state.
- **A3** Run against a repository at a known commit, the generator writes that commit.
- **A4** Run against the same repository once clean and once dirty, the generator writes
  `dirty = false` then `dirty = true`, with the commit unchanged — with the generator's own
  output written outside that repository, so the clean run observes a genuinely clean tree.
- **A5** A compiled sentinel commit is never paired with `dirty == true`.
- **A6** The hermetic tests seal the git environment — `GIT_DIR`, `GIT_WORK_TREE` and
  `GIT_INDEX_FILE` cleared, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` at `/dev/null` — for
  the generator invocation as well as for the test's own git calls.
- **A7** The suite is green on a dirty worktree and after a HEAD move, with no clearing of
  `.build/plugins` and no other build-cache surgery.

## Child work found

**1. The compiled build identity can be stale in a freshly built binary.** Measured above:
when llbuild considers the build plan up to date the prebuild command does not run, so
`BuildInfo.current.commit` can name a commit that is not this checkout's `HEAD` while
`swift build` reports success. This is a defect in PRO-0030's own promise — a build says which
build it is — and it is left standing by this spec, which only stops the test suite from
asserting something it cannot know.

It is not fixed here for two reasons. It is a change to the build mechanism rather than to a
test, so it carries rebuild-cost consequences on every build that this id's gate-reliability
scope does not cover. And the obvious fix named in the brief does not apply: a prebuild
command has no declared inputs to add, so a real fix means a different mechanism, which is
its own spec.

**2. Nothing on the release path runs the suite.** Raised by the out-of-family review and
verified: no workflow in `.github/workflows/` invokes `swift test`. So a binary that silently
reported a placeholder identity would still ship green, because the tests that would catch it
never execute outside a developer's terminal. That is a gap in what PRO-0030's suite can
promise, and it is not closed by anything in this spec — adding a CI test job is a separate
piece of work with its own runtime and cost questions.

**3. `TakeoverWiringTests` fails intermittently in a full-suite run.** `shows.count → 0`
where 1 is expected, at `TakeoverWiringTests.swift:122`; green 3/3 in isolation. Verified
pre-existing by reverting this branch's two files to `da4f48f`, rebuilding, and running the
full suite five times, where it fired on the fifth. It is the shared-singleton hazard the
runner contract documents. This branch makes it fire more often by adding subprocess load, so
it is worth someone's attention: it is the same species of false red this feature exists to
remove, in a suite this feature does not own.

Neither of the first two is specced here per the runner contract; all three are recorded for
the orchestrator.

## Triage — 2026-08-15

**Verdict: Ready for Plan.** S1. The subject is a test suite in a repository with no product
surface at stake, the change is confined to one test file plus one comment, and the decision
it turns on was settled by measurement rather than by preference.

### What a reader will see change

Someone running the checks after moving to a different commit, or with a file open and edited,
sees them pass. Today they can see a failure that reads as though two versions of the app
disagree with each other, when nothing is wrong and the only fix is to delete a hidden folder
they would have no reason to know about. The checks still catch the thing they were built to
catch — a build that has lost track of which build it is — and they now also catch something
they never did, which is the app failing to notice that someone has unsaved changes.

### Assumptions

- The plugin's staleness is left in place and recorded as separate work, because fixing it
  changes what every build costs and this item is about a false alarm in the checks.
- The corrected comment is included even though it changes no behaviour, because it is the
  sentence that caused the wrong diagnosis in the first place.
- The suite keeps failing loudly if the app cannot identify itself at all; only the comparison
  against the live folder is dropped.

### Out-of-family review

`grok-4.6` at `xhigh`, read-only, 2026-08-15. The first call died mid-reasoning against the
300s deadline while opening files; it was re-run with file reading forbidden and every fact
inlined, which is the failure and the remedy the runner contract already documents.

Eight findings. **Five accepted and folded into the decisions above:** the hermetic test's own
output would have dirtied the repository it was measuring, so the clean run would have
observed the test's own artefact; `--short=12` is a minimum width and an exact-length check is
a latent false alarm; `GIT_DIR` and friends override `-C`, and inherited global config carries
hooks and signing, so the environment needs sealing for the script as well as for the test;
`unavailable` is reachable in a healthy checkout, so the strong clause needs the live git call
as a precondition; and a sentinel commit paired with `dirty == true` is an impossible state
worth pinning cheaply.

**Two rejected with reasons.** The `.git`-is-a-file worktree trap is already handled — the
script gates on `-e` rather than `-d` and its comment says why — and the reviewer could not
see that, having been told not to read files. "Assert the generated symbol is a bool literal"
is not expressible in Swift, where the property is typed `Bool` by construction.

**One accepted as child work:** that no workflow runs `swift test`, so a placeholder identity
could still ship green. True, verified, and larger than this id.

The first finding is the one that mattered: the hermetic test as originally drafted would have
been wrong, and would most likely have failed on its first run rather than passing falsely.

### A third instance, and a conclusion this note originally got wrong

`compiledVersionMatchesPlist` compared the compiled version against the live `Info.plist` —
the same construction, and one the brief never named. It was checked, **cleared, and the
clearance was wrong**, which is worth recording because the wrong answer was the plausible one.

The first check changed the plist version to `9.9.9` with the plan warm and re-ran: green. The
conclusion drawn was that a file-shaped input is materially different from a HEAD move, because
editing a file gives llbuild work to do where moving HEAD changes no file at all.

Changing it **back** is what breaks it. The revert did not reschedule the generator, so the
compiled constant kept `9.9.9` while the plist read `0.1.0`, and the assertion failed. It
surfaced by accident: reverting the fixture after the first check left the stale value behind,
and the next full run went red. So the rule is not "file inputs are safe" — it is that
rescheduling is not something this mechanism promises in either direction, and the failure
lands where it costs most: a reverted release, or a version bump dropped during a rebase.

Fixed the same way as the commit, in commit `d4a1565`. The equality goes; where the plist is
readable the compiled version must not be `unknown` and must begin with a digit. That the
generator reads the plist is already proven where the test owns the plist
(`withoutGitTheIdentityIsStillReal`, `pathWithSpaces`), and the release path is guarded
independently by `scripts/check-release-version.sh`, so nothing load-bearing rested on the
comparison. Verified against the stale state itself: with the compiled value at `9.9.9` and
the plist at `0.1.0`, the suite passes 27/27 where it previously failed.

### A pre-existing flake this work did not cause but does provoke

`TakeoverWiringTests.swift:122` (`a batch that starts on the accessibility plane raises it at
the first synthetic step`) fails intermittently in a full-suite run with
`(h.takeover.shows.count → 0) == 1`. It passes 3/3 in isolation.

**It is not caused by this change, and that was established rather than assumed.** With both
changed files reverted to `da4f48f` and rebuilt, the full suite was run five times and the
same assertion failed on the fifth. It is the shared-singleton hazard the runner contract
already documents, surfacing through scheduling order.

This change does raise how often it fires — roughly half of full-suite runs here, against one
in five on the base — because the two new hermetic tests spawn git and shell subprocesses and
that shifts scheduling for the suites running alongside them. Worth flagging plainly, since a
flaky merge gate is the exact complaint this feature exists to answer: fixing one false red
while another remains is a partial answer. It is another feature's harness, so it is reported
rather than edited.
