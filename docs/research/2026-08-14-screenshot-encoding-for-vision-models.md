# Strategic Configuration of macOS Computer-Use MCP Servers for Visual Language Models

## Executive Summary

*   **(High Confidence)** Visual Language Models (VLMs) process image inputs through rigid, mathematically defined tokenization grids that severely penalize arbitrary display resolutions. Relying on provider-side auto-downscaling introduces coordinate mapping misalignment and uncontrolled token inflation. A macOS Model Context Protocol (MCP) server must preemptively scale screenshots client-side to harmonize with the specific geometric boundaries of the target model (e.g., exactly 768px intervals for Gemini, or 1568px to 2576px long-edge ceilings for Claude).
*   **(High Confidence)** JPEG compression is fundamentally hostile to synthetic User Interface (UI) workloads. The Discrete Cosine Transform (DCT) and chroma subsampling inherent in the JPEG algorithm introduce ringing artifacts and color fringing along high-contrast text edges. Empirical eye-tracking studies demonstrate this degradation increases visual search time by 1.4 to 1.9 seconds per screen region and severely degrades a VLM's ability to ground small UI components.
*   **(High Confidence)** WebP, deployed in high-quality lossy configurations (Q80-Q90) or lossless mode, is the optimal container format for UI screenshots. It delivers network payloads 25% to 35% smaller than PNG at equivalent perceptual fidelity, directly reducing uplink latency in high-frequency agentic loops without sacrificing the sharp edge definition required for accurate optical character recognition (OCR).
*   **(Medium Confidence)** Modern production harnesses universally employ a bifurcated resolution architecture: returning a heavily compressed, low-resolution overview to the model for macroscopic navigation, coupled with an explicit, on-demand `zoom` tool that returns a 1:1 native-resolution crop of a requested bounding box. This specific design pattern increases VLM grounding accuracy on dense professional interfaces from baseline scores of under 20% to over 70%.
*   **(High Confidence)** macOS Retina displays capture screenshots at a Device Pixel Ratio (DPR) of 2, meaning physical pixel dimensions double the logical screen coordinates. An MCP server must manage a persistent affine transformation matrix to translate the model's pixel predictions from the downscaled vision space back to the operating system's logical coordinate space for accurate mouse execution.

### Vision Tokenizer Architectures and Provider Ceilings

The economic and latency profiles of computer-use agents are dictated by how frontier model providers map raw pixels to their transformer's internal token space. Unlike text, where tokenization relies on subword dictionaries, visual tokenization is inherently geometric. For a macOS MCP server, such as the proposed "Proctor" system, to operate efficiently, it must intercept and manipulate the display buffer before transmission, tailoring the geometry to the specific model family in use to avoid token waste and coordinate corruption.

The Anthropic Claude architecture employs an area-based tokenization formula, where image tokens are calculated roughly as `(width × height) / 750` [claudecodecamp.com](https://www.claudecodecamp.com/p/images-cost-3x-more-tokens-in-claude-opus-4-7). However, this is bounded by strict dimensional ceilings that dictate how the model's vision encoder receives the data. For the Claude 4.6 family and earlier iterations, the API enforces a hard limit of 1,568 pixels on the longest edge, or approximately 1.15 megapixels in total area [claude.com](https://claude.com/blog/best-practices-for-computer-and-browser-use-with-claude). Any image exceeding this threshold is silently downscaled by the provider, preserving the aspect ratio, until it fits within the 1.15-megapixel budget [platform.claude.com](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool). This auto-downscaling presents a critical failure mode for macOS computer-use agents. Because the MCP server is unaware of the exact scaling factor applied asynchronously by the API, the coordinate outputs generated by the model will map to the downscaled coordinate grid, not the native screen, resulting in systematic click misses that land consistently offset from the intended target [jatinbansal.com](https://jatinbansal.com/ai-engineering/computer-use-agents/). With the introduction of the Claude 4.7 and 4.8 families, Anthropic expanded this ceiling significantly, allowing up to 2,576 pixels on the long edge, which equates to approximately 3.75 megapixels [claude.com](https://claude.com/blog/best-practices-for-computer-and-browser-use-with-claude). While this expansion permits a native 1:1 coordinate mapping for most modern displays, it carries a severe economic penalty. An image sent at this maximum resolution will consume nearly three times the tokens of the previous 1568px limit, and paired with a newer tokenizer that produces 1.0x to 1.35x more tokens for the same input, this severely limits the viable temporal length of agentic context windows before hitting maximum token ceilings [claudecodecamp.com](https://www.claudecodecamp.com/p/images-cost-3x-more-tokens-in-claude-opus-4-7).

OpenAI's GPT-4o and Operator/CUA models utilize a completely divergent, patch-based tiling algorithm. When an image is submitted with `detail: "high"`, the API first mathematically scales the image so that it fits entirely within a 2048x2048 pixel bounding box [openai-hd4n6.mintlify.app](https://openai-hd4n6.mintlify.app/docs/guides/images). Subsequently, it scales the image again so that its shortest side is exactly 768 pixels long. The resulting canvas is then divided into a rigid grid of 512x512 pixel tiles. The total token cost is calculated as a base fee of 85 tokens for a low-resolution "master thumbnail," plus an additional 170 tokens for every 512x512 tile required to cover the image [genai.stackexchange.com](https://genai.stackexchange.com/questions/1902/what-is-the-maximum-number-of-images-that-a-single-request-may-contain-with-gpt4). <INFERENCE from="https://openai-hd4n6.mintlify.app/docs/guides/images, https://jatinbansal.com/ai-engineering/computer-use-agents/">Because this algorithm strictly relies on 512px chunks, an MCP server that arbitrarily captures a standard 16-inch MacBook Retina screen (e.g., 3456x2234) will force the API to generate a highly inefficient tiling grid. Pre-scaling the image client-side to a resolution that cleanly divides by 512px after the 768px shortest-edge constraint is applied minimizes "wasted" patches that only contain a sliver of screen data, thereby optimizing token spend.</INFERENCE> Furthermore, OpenAI's computer-use specific models deliberate omit automatic downscaling for original-detail inputs, meaning unoptimized Retina screenshots will pass directly into the token space without guardrails, resulting in massive, uncontrolled token inflation if the MCP server fails to manage the resolution proactively [developers.openai.com](https://developers.openai.com/api/docs/guides/tools-computer-use).

Google's Gemini models (including 1.5 Pro, 2.0 Flash, and 3.1 Pro) operate on a rigid, threshold-based tiling logic that heavily penalizes unoptimized boundaries. If an image is 384x384 pixels or smaller, it consumes a flat baseline of 258 tokens. For any image exceeding this dimension, Gemini mathematically divides the image into 768x768 pixel tiles [gemini-api.apidog.io](https://gemini-api.apidog.io/doc-965860). The token cost is calculated using a strict ceiling function: `ceil(Width / 768) × ceil(Height / 768) × 258 tokens` [dev.to](https://dev.to/kushaagr/can-image-tokens-cost-less-than-text-tokens-explaining-gemini-api-image-token-economics-422c). This specific algorithmic choice creates extreme token cliffs. An 800x800 pixel image, crossing the 768px boundary by a mere 32 pixels in both directions, triggers a 2x2 grid calculation, ultimately costing 1,032 tokens. Pre-cropping or downscaling that same image to 768x768 pixels reduces the cost to a single tile of 258 tokens—a 75% cost reduction with virtually zero loss in perceptual data for the model [dev.to](https://dev.to/kushaagr/can-image-tokens-cost-less-than-text-tokens-explaining-gemini-api-image-token-economics-422c).

### The Physiology of UI Compression: Empirical Evidence on JPEG and Text Legibility

When engineering a computer-use MCP server, selecting the correct image compression algorithm is not merely a matter of conserving file size; it fundamentally dictates the capability of the VLM to parse structural text and layout. Visual Language Models rely entirely on high-frequency visual data to ground coordinates and read small typography. Screenshots are synthetic images characterized by hard, high-contrast edges, such as black text on a white background, sharp UI borders, and distinct color demarcations.

Empirical data conclusively demonstrates that JPEG compression is actively hostile to synthetic UI workloads. The JPEG format relies on the Discrete Cosine Transform (DCT) and chroma subsampling, mechanisms optimized exclusively for the smooth gradients and organic transitions of natural photography [scanly.co](https://scanly.co/blog/jpeg-compression-artifacts-explained). When applied to the sharp edges of UI text, JPEG introduces severe ringing artifacts (often referred to as the Gibbs phenomenon) and color fringing [lifetips.alibaba.com](https://lifetips.alibaba.com/tech-efficiency/choose-the-right-image-format-for-screenshots). A 2022 controlled eye-tracking study conducted by the Carnegie Mellon Human-Computer Interaction Institute measured the direct impact of these artifacts on cognitive load. The study found that reading JPEG-compressed text required 19% longer fixation durations and 2.3 times more saccades to resolve characters, effectively slowing down visual processing [lifetips.alibaba.com](https://lifetips.alibaba.com/tech-efficiency/choose-the-right-image-format-for-screenshots). A subsequent 2023 study by the University of Waterloo Human Factors Lab noted that developers spent 1.4 additional seconds per JPEG screenshot verifying whether a visual anomaly was a real UI bug or merely a compression artifact [lifetips.alibaba.com](https://lifetips.alibaba.com/tech-efficiency/choose-the-right-image-format-for-screenshots).

For VLMs, this visual degradation translates directly into task failure. Comprehensive benchmarking suites, such as CompressVLMBench—which evaluated over one million compressed images across 11 distinct codecs and 9 different VLMs—demonstrate that frontier models suffer massive performance gaps when digesting low-bitrate, lossy images [arxiv.org](https://arxiv.org/html/2512.20901v2). Because VLMs process images in localized patches (e.g., 28x28 or 32x32 pixels), the introduction of DCT artifacting within a discrete patch fundamentally disrupts the model's ability to map the visual representation to its internal linguistic tokens, causing textual legibility to collapse entirely at lower resolutions [dev.to](https://dev.to/kushaagr/can-image-tokens-cost-less-than-text-tokens-explaining-gemini-api-image-token-economics-422c). While VLMs often outperform traditional OCR models on noisy, unstructured data (like skewed photographs of receipts), they require clean, artifact-free edges to reliably parse dense, high-frequency interfaces like spreadsheets or code editors [youtube.com](https://www.youtube.com/watch?v=wMhs0GTZvo0). As an illustrative corollary, when compressing a photo of a whiteboard using JPEG, the macroscopic diagrams survive the compression, but the handwritten footnotes in the corners become unreadable smudges; similarly, VLMs will hallucinate or fail to ground specific telemetry or textual data when forced to parse artifact-heavy UI inputs [medium.com](https://medium.com/@arthurpro/your-llm-is-a-jpeg-of-the-internet-4bf6c67986ea).

### Container Economics: PNG vs. WebP vs. JPEG for GUI Workloads

Given the toxicity of JPEG to UI components, MCP servers must adjudicate between PNG and WebP formats. While PNG offers mathematically lossless compression and is broadly considered the gold standard for preserving pixel integrity and alpha-channel transparency [blog.fileformat.com](https://blog.fileformat.com/image/best-image-formats-for-ai-training-data-png-vs-jpeg-vs-webp-vs-tiff/), it generates excessively large payloads. A 4K macOS screenshot saved as an uncompressed or standard PNG can consume 32 MB of RAM during capture and 120 MB of disk I/O during export. This mass data movement becomes a severe network and local-compute bottleneck in autonomous loops where an agent may request a fresh screenshot every few seconds [lifetips.alibaba.com](https://lifetips.alibaba.com/tech-efficiency/choose-the-right-image-format-for-screenshots).

WebP emerges as the optimal container for UI screenshots operating within a strict network and size budget. Developed by Google, WebP utilizes advanced block-based prediction models and modern entropy coding to deliver files that are 25% to 35% smaller than PNGs at identical perceptual quality levels [scanly.co](https://scanly.co/blog/jpeg-compression-artifacts-explained). Crucially, WebP supports both lossless and high-quality lossy modes (e.g., Q80 or Q85) that successfully avoid the destructive ringing artifacts associated with JPEG while maintaining the crisp text edges required by VLMs [aiimageedit.org](https://aiimageedit.org/posts/image-compression-optimization-ai).

Network simulations for multimodal agent pipelines further validate the superiority of WebP. In systems like Sema, which optimize Wide Area Network (WAN) transport for visual agent streams, transmitting a 1080p screenshot as a raw PNG requires approximately 950 KB, whereas a WebP at quality 80 reduces the payload to roughly 700 KB. At a 5 Mbps uplink speed, the WebP upload takes approximately 1.1 seconds—accounting for over 60% of the end-to-end action latency. Utilizing WebP significantly cuts this latency without degrading the exact-match action accuracy of the agent, which remains within 0.7 percentage points of the raw, uncompressed baseline [arxiv.org](https://arxiv.org/pdf/2604.20940). Therefore, a macOS MCP server should encode display buffers using WebP Lossless or WebP Lossy (Q80-Q90) to minimize transmission latency to the LLM endpoint while preserving the sharp demarcations of small UI fonts [lifetips.alibaba.com](https://lifetips.alibaba.com/tech-efficiency/choose-the-right-image-format-for-screenshots, https://blog.fileformat.com/image/best-image-formats-for-ai-training-data-png-vs-jpeg-vs-webp-vs-tiff/).

### Production Telemetry: How Frontier Harnesses Handle Downscaling

An analysis of existing production harnesses reveals a strong architectural convergence on client-side resizing using high-quality resampling filters, explicitly rejecting reliance on cloud-provider auto-scaling algorithms.

**Anthropic Computer-Use Reference Implementation:** The official Docker-based reference implementation for Claude's computer use captures the XFCE desktop buffer utilizing the `mss` python library. The implementation explicitly warns developers to maintain screenshot resolutions at XGA (1024x768) or WXGA (1280x800) for optimal reliability [glama.ai](https://glama.ai/blog/2024-10-22-automate-computer-using-claude). If the native virtual display exceeds this, the Python driver uses the Python Imaging Library (PIL) to scale the image down, strictly utilizing the `Image.Resampling.LANCZOS` filter [digitalapplied.com](https://www.digitalapplied.com/blog/anthropic-computer-use-api-guide). <INFERENCE from="https://www.digitalapplied.com/blog/anthropic-computer-use-api-guide, https://scanly.co/blog/jpeg-compression-artifacts-explained">Lanczos resampling is mathematically chosen over Bilinear or Bicubic filters because it utilizes a sinc kernel that preserves high-frequency details—such as text edges and small icons—significantly better during decimation, preventing the UI from becoming an unreadable blur.</INFERENCE> The image is subsequently saved to an in-memory buffer as an optimized PNG before base64 encoding [digitalapplied.com](https://www.digitalapplied.com/blog/anthropic-computer-use-api-guide).

**OpenAI Operator / CUA:** OpenAI's Computer-Using Agent framework requires developers to manage the coordinate space mathematically through bi-directional affine transformations. The official documentation advises that if `detail: "original"` consumes excessive tokens, the loop driver must downscale the image client-side. Crucially, the driver must retain the specific scale factor in memory so that when the model outputs a click coordinate based on the reduced image, the driver can upscale that coordinate back to the native display resolution before executing the OS-level mouse event [developers.openai.com](https://developers.openai.com/api/docs/guides/tools-computer-use). A failure to map these coordinates bidirectionally is documented as the leading cause of "near-miss" click errors [jatinbansal.com](https://jatinbansal.com/ai-engineering/computer-use-agents/). Furthermore, OpenAI recommends standardizing the virtual display to 1440x900 or 1600x900, and explicitly mandates a 0.3-second sleep after each click to ensure the subsequent screenshot does not capture half-rendered menus or mid-transition animations, which confuse the model [developers.openai.com](https://developers.openai.com/api/docs/guides/tools-computer-use, https://jatinbansal.com/ai-engineering/computer-use-agents/).

**Browser Use / Playwright MCP:** Harnesses operating exclusively in the browser context, such as the Vercel-backed `agent-browser` or `fast-playwright-mcp`, heavily prioritize the extraction of the Document Object Model (DOM) and Accessibility Trees over raw pixel analysis to drastically conserve tokens [github.com](https://github.com/tontoko/fast-playwright-mcp, https://bitbasti.com/blog/moving-toward-code-based-agents-agent-browser). However, when visual fallback is absolutely required, `fast-playwright-mcp` exposes image compression options directly to the agent, allowing formats to be swapped to JPEG with granular quality controls (`quality: 1-100`) and a `maxWidth` parameter for aggressive token optimization [github.com](https://github.com/tontoko/fast-playwright-mcp). The `agent-browser` tool defaults to 1280x720 viewports, deliberately hiding native scrollbars to maintain visual consistency for the model across different platforms [github.com](https://github.com/vercel-labs/agent-browser, https://agent-browser.dev/configuration).

**Claude Code:** Anthropic's terminal-based autonomous agent handles macOS Retina displays uniquely. Because a 16-inch MacBook Pro operates natively at 3456x2234, passing this buffer directly would trigger a massive token penalty and subsequent API rejection. To circumvent this, Claude Code automatically captures the display and aggressively downscales it to approximately 1372x887, preserving the aspect ratio [code.claude.com](https://code.claude.com/docs/en/computer-use). Users are explicitly instructed not to alter their system resolution; if text becomes illegible after the internal downscale, they must increase the target application's font size rather than attempting to bypass the agent's scaling logic [code.claude.com](https://code.claude.com/docs/en/computer-use).

### The Bifurcated Resolution Strategy: Overview and On-Demand Zoom

The central architectural dilemma of computer-use agents lies in the conflict between context window economics and pixel-level grounding. High-resolution screenshots (e.g., native 4K) provide excellent text legibility but consume exorbitant token budgets, fundamentally limiting the agent's memory length and temporal horizon. Conversely, aggressively scaled images (e.g., 1024x768) save tokens but destroy the visual fidelity required to interact with tiny UI targets like system tray icons, checkboxes, or dense data tables.

To resolve this, advanced MCP architectures implement a bifurcated resolution design pattern. This involves returning a heavily compressed, low-resolution overview by default, complemented by an on-demand, native-resolution `zoom` or `crop` tool. In this architectural pattern, the MCP server operates as the custodian of a persistent, native-resolution frame buffer. It serves the downscaled overview (e.g., 1024x768) to the LLM for general, token-optimized navigation, allowing the model to grasp the macroscopic layout. When the LLM determines it needs to read dense UI text or interact with a micro-element, it invokes the zoom tool, passing a specific bounding box coordinate array. The MCP server then executes an on-demand, high-fidelity regional crop, extracting exactly that region from the uncompressed native buffer and returning it 1:1 to the model.

Empirical data overwhelmingly supports the efficacy of this specific pattern:
*   **ScreenSpot-Pro Benchmark:** A rigorous benchmark designed to test GUI grounding in high-resolution, professional desktop software across 1,832 examples. Early multimodal LLMs achieved a dismal 18.9% accuracy on this dataset, struggling severely with large canvas sizes [medium.com](https://medium.com/@adnanmasood/the-hardest-easy-problem-in-ai-the-state-of-computer-use-agents-a7e3aea7fa3a). 
*   **ScreenSeekeR Implementation:** By applying an agentic framework that iteratively crops and zooms into probable regions to remove irrelevant visual distractions, the ScreenSeekeR architecture boosted the OS-Atlas-7B model's performance from 18.9% to 48.1%—a 254% relative improvement—without requiring any additional fine-tuning [arxiv.org](https://arxiv.org/html/2504.07981v1, https://likaixin2000.github.io/papers/ScreenSpot_Pro.pdf).
*   **MEGA-GUI (Bidirectional ROI Zoom):** This architecture takes the pattern further by implementing a closed-loop control mechanism. It uses a base model to aggressively crop inward (zoom-in) for refinement, and outward (zoom-out) for error recovery, targeting an optimal Region of Interest (ROI) size of 1000 pixels. This synergistic composition established a new state-of-the-art on ScreenSpot-Pro, reaching 73.18% accuracy [arxiv.org](https://arxiv.org/html/2511.13087v1).
*   **ManiCoG (Manipulation Chain of Grounding):** Applying a coarse-to-fine focus mechanism to the TianXi-Action-7B model boosted accuracy from 51.9% to 57.8%, proving that optimizing the inference pathway via zooming yields massive dividends over attempting to process the whole screen at once [openreview.net](https://openreview.net/pdf/923b5639c2327c8a2edf2c14db926a0b4866f1fb.pdf).

Anthropic explicitly builds this paradigm into their internal schema. The Claude 4.6 and 4.7 models support a native `enable_zoom: true` configuration in the tool definition, allowing the model to autonomously inspect specific dense UI regions at higher resolution before committing to a click event [claude.com](https://claude.com/blog/best-practices-for-computer-and-browser-use-with-claude, https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool).

## Secondary: What is the current state, and what is the strongest supporting evidence for it?

The current operational state of computer-use agents is defined by a rapid transition from custom, hard-coded API wrappers to generalized, vision-primary interfaces. Systems like Claude Computer Use, UI-TARS, and Agent S2 have validated that pure visual processing—where the model relies solely on screen pixels rather than inspecting underlying accessibility trees—is viable for general-purpose desktop control [github.com](https://github.com/temm1e-labs/temm1e). 

However, the supporting evidence reveals that raw capability remains heavily bottlenecked by the environment's complexity and the compounding nature of long-horizon tasks. On the OSWorld 2.0 benchmark—a demanding long-horizon evaluation where median human completion times average 1.6 hours—the best frontier systems (such as Claude Opus 4.8) successfully complete only 20.6% of tasks [medium.com](https://medium.com/@adnanmasood/the-hardest-easy-problem-in-ai-the-state-of-computer-use-agents-a7e3aea7fa3a). The primary culprit is error compounding: a misgrounded click at step 40 can silently corrupt the application state, creating an unrecoverable trajectory [medium.com](https://medium.com/@adnanmasood/the-hardest-easy-problem-in-ai-the-state-of-computer-use-agents-a7e3aea7fa3a). 

To mitigate this, state-of-the-art implementations heavily utilize "Set-of-Mark" (SoM) overlays. Before passing the screenshot to the model, the environment annotates interactive elements with numbered labels. This transforms the complex coordinate-guessing task into a simpler visual selection task, reportedly reducing output information complexity by a factor of 3.75x and significantly reducing errant clicks [github.com](https://github.com/temm1e-labs/temm1e).

## Secondary: What are the contrasting viewpoints or competing evidence?

A primary architectural debate within the agent ecosystem centers on whether systems should rely entirely on pixels (Vision-Primary) or leverage underlying structural data (DOM-Primary). 

The Vision-Primary approach, championed by Anthropic and OpenAI, argues that relying on screenshots makes the agent universally applicable across any operating system, legacy desktop application, or obfuscated web canvas [github.com](https://github.com/temm1e-labs/temm1e, https://www.digitalapplied.com/blog/anthropic-computer-use-api-guide). If a human can see it and click it, the model can operate it, effectively circumventing bot-protection mechanisms that block traditional DOM-scraping tools.

Conversely, the DOM-Primary approach, utilized by projects like `fast-playwright-mcp` and `agent-browser`, argues that pixel-based input is computationally wasteful, slow, and non-deterministic. Passing an accessibility tree operates purely on structured textual data, bypassing the need for expensive Vision Language Models entirely. This approach is significantly faster, 3x to 10x cheaper in token costs, and eliminates the inherent ambiguity of bounding box coordinate predictions [github.com](https://github.com/tontoko/fast-playwright-mcp, https://github.com/temm1e-labs/temm1e).

## Secondary: What changed recently, and what is the trajectory?

The trajectory of VLM visual encoders is aggressively scaling upward to support higher native resolutions, slowly reducing the reliance on client-side scaling gymnastics. Anthropic's jump from a 1568px ceiling in Claude 4.6 to 2576px in Opus 4.7 represents a massive 2.6x increase in pixel capacity, directly targeting the needs of computer-use agents requiring pixel-accurate clicks without manual affine transformations [claudecodecamp.com](https://www.claudecodecamp.com/p/images-cost-3x-more-tokens-in-claude-opus-4-7).

Simultaneously, research is shifting toward decoupling perception from reasoning to optimize inference pipelines. Frameworks like SPARC (Separating Perception And Reasoning Circuits) allow models to dynamically expand their token budget during inference. They run global searches at lower image resolutions and allocate high-resolution processing only to selected regions, preventing long, disorganized contexts where a single perceptual mistake cascades into a total reasoning failure [researchgate.net](https://www.researchgate.net/publication/400584069_SPARC_Separating_Perception_And_Reasoning_Circuits_for_Test-time_Scaling_of_VLMs).

Furthermore, Microsoft's Phi-Ground model family and the introduction of continuous dynamic resolution architectures (such as Qwen2-VL's implementation of 2D-RoPE) demonstrate that future encoders will natively process varied aspect ratios and resolutions without the destructive need for padding or rigid square-tiling [techrxiv.org](https://www.techrxiv.org/doi/pdf/10.36227/techrxiv.176620829.92520878/v1).

## Recommended Next Steps

1.  **Implement Client-Side Lanczos Scaling Pipeline:** Configure the Proctor macOS MCP server to intercept the Retina display buffer (e.g., 3456x2234) and utilize `Image.Resampling.LANCZOS` to generate a base 1280x800 overview image. Rationale: Ensures text edges remain sharp during decimation and prevents opaque, non-deterministic coordinate scaling by the provider APIs.
2.  **Standardize on WebP Q85 Encoding:** Replace standard PNG capture mechanisms with WebP at quality level 85. Rationale: Eliminates the destructive ringing artifacts of JPEG while cutting network payload sizes by ~30% compared to PNG, directly improving the cycle time of the agentic loop without corrupting VLM OCR capabilities.
3.  **Develop a Native-Resolution Cropping Tool:** Implement an `enable_zoom` compliant tool within the MCP schema. Rationale: Allows the server to accept a coordinate bounding box from the LLM, fetch the corresponding region from the *unscaled* in-memory frame buffer, and return a lossless 1:1 pixel crop to solve dense UI grounding failures that occur when the model attempts to read the overview image.
4.  **Enforce Strict Affine Transformation Tracking:** Establish a coordinate mapping state manager within the MCP server. Rationale: macOS Device Pixel Ratio (DPR) creates a persistent mismatch between OS-level logical coordinates (which the mouse uses) and physical pixels (which the model sees). The server must mathematically upscale the VLM's click predictions to match the native display before dispatching OS events.
